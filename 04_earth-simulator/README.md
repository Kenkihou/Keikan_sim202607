# PLATEAU 背景レイヤー（Three.js）

国土交通省 **PLATEAU** の 3D Tiles（建築物 LOD2）を、
[**3d-tiles-renderer (3DTilesRendererJS)**](https://github.com/NASA-AMMOS/3DTilesRendererJS) と
[three.js](https://threejs.org/) で描画する、**ビルド不要**（バンドラ不要・ES Modules 直読み）の
Web アプリです。

**用途**: Three.js で自作の 3D モデリングを行う際の「背景・周辺の街並み」として PLATEAU
建物 + **地形（Terrain）**を表示する土台。PLATEAU 建物・地形・自作モデルが**同じ Three.js
シーン・同じ renderer**に載るので、カスタムマテリアル・ステンシル・クリッピング断面など
Three.js の機能をそのまま適用できます（CesiumJS では難しい部分）。

指定した緯度経度（既定=京都駅/下京区）を原点 `(0,0,0)` に据えます。

**設計方針：注目地点まわりだけを高速描画**。PLATEAU の LOD2 葉タイルは1枚5〜7MBと重く、
広域を一度に読むと現実的な時間で終わらない（実測済み）。そこで**建物は「注目地点の周り
＝約9タイル（東西 `LOCAL_WIDTH_EW`m ×南北 `LOCAL_WIDTH_NS`m の矩形）」だけ**を読み込み、
広域は捨てて高速化しています。注目地点は既定で原点（自作モデルの位置）で、**画面右下の
地図（国土地理院）をクリックして拡大 → 任意地点をクリック**するとそこへ建物が移動します
（旧タイルは自動で破棄）。**地形（航空写真）は距離制限せず**全域に敷くので、建物が無い範囲
も地面は続き見た目は破綻しません。全11区ぶんの `TilesRenderer` を用意し、共有の矩形マスク
（`LoadRegionPlugin` + `OBBRegion`）で注目地点を含む区の近傍タイルだけを読みます。矩形なので
選ばれる範囲は東西・南北にきれいな長方形になります（円形(Sphere)マスクだと PLATEAU のタイル
境界が不規則なため、選ばれる範囲がいびつな塊になる）。

**地形と建物の高さ**: PLATEAU の地形（Quantized Mesh）を建物と**同じ緯度経度の
`ReorientationPlugin` で整列**して重ねています。両者が同一の座標系（ECEF）に載るため、
**建物は自動的に地形の標高（地盤高さ）の上に載ります**。原点の地表が `Y=0` になるよう
`ORIGIN_HEIGHT`（原点の楕円体高）を設定してあるので、自作モデルは `Y=0` 基準で地面に
置けます。

**中心の切り抜き（カットモデル）**: 注目地点を中心とした「一辺 N m の四角柱」の内側だけを
残すカットモデル表示ができます。**建物の切り口は灰色＋黒い斜線ハッチで塗りつぶし**、**地形の切り口は青い太線
（地盤ライン）**で表現します。HUD で **ON/OFF・一辺の長さ（50〜500m を 50m 刻み）・地形も
切り抜くか** を切り替えられます。断面は GPU のステンシルではなく**CPU で交線を計算して
ポリゴン化**しています（PLATEAU のデータが水密でないため。下記「仕組み」参照）。

**地形の航空写真／地図**: 地形には国土地理院タイルをテクスチャとして貼れます。HUD 左上の
ボタンで **航空写真 / 地理院地図(標準) / 淡色地図 / なし** を切り替えられます
（`ImageOverlayPlugin` + `XYZTilesOverlay`）。

## ファイル構成

`index.html` は骨組み（HTML・CSS・import map）だけで、実装は `js/` 以下の機能別モジュールに
分かれています。読み込むのは `js/main.js` だけで、あとは ES Modules が解決します。

| ファイル | 行数 | 役割 |
|---|---|---|
| `index.html` | 141 | HTML・CSS・import map。`<script type="module" src="js/main.js">` のみ |
| `js/config.js` | 141 | **設定値だけ**（tileset URL・原点・読み込み範囲・色など）。何にも依存しない |
| `js/core.js` | 92 | DOM・Three.js 基本セット（renderer/scene/camera/controls/光源）・共有状態 |
| `js/section.js` | 770 | 中心の切り抜きと断面（クリップ面／建物断面=灰＋黒ハッチ／青い地盤ライン／土・等高線） |
| `js/tiles.js` | 535 | PLATEAU の読み込み全般（建築物・地形＋航空写真・注目地点の移動） |
| `js/viewareas.js` | 348 | 眺望空間保全地域のポリゴンを地形に沿わせて重ねる |
| `js/ui.js` | 190 | 左上パネルと、右下の国土地理院地図（クリックで拡大 → 地点選択） |
| `js/usermodel.js` | 300 | **親アプリ(01)から受け取った自作モデル**の配置・接地・向き・微調整のUI |
| `js/main.js` | 138 | 組み立て・描画ループ・`window.__dbg` |
| `shp2json.py` | — | シェープファイル(EPSG:2448) → WGS84 JSON の変換（オフラインで一度だけ実行） |
| `contour2surface.py` | — | 規制値等高線 → 眺望規制の標高面（経緯度の規則格子）への変換 |

**依存の向きは一方向**で、循環しないようにしてあります。

```
config（設定値だけ）
  └ core（DOM・Three.js基本・共有状態・再構築フラグ）
      ├ section（切り抜き＋断面）
      │   ├ tiles（建物・地形・注目地点の移動）
      │   │   └ ui（左上パネル・右下の地図）
      │   │       └ usermodel（自作モデルの配置・接地）
      │   └ viewareas（眺望空間保全地域）
      └ main（組み立て・描画ループ）
```

- **⚠️ 循環を避ける肝は「再構築フラグを `core.js` に置く」こと**。断面や眺望ポリゴンの
  作り直しは `core.js` の `dirty` レジストリ（`markSectionDirty()` / `markViewAreaDirty()`）で
  伝える。こうすると `tiles.js` が `section.js` / `viewareas.js` を import せずに
  「汚れた」と伝えられる。逆向きの import が生まれないので循環しない。
- 描画ループのスロットリング状態（`sectionLastBuild` など）は `main.js` が持つ。
- デバッグ用の `window.__dbg` は `main.js` で1か所にまとめて公開している。

## 実行方法

ES Modules と import map を使うため、**ローカルの HTTP サーバー経由**で開きます。
親アプリ（01）と一緒に使う場合は下の「開発時の起動」を参照（サーバーを別に立てる必要はない）。
このアプリ単体で開くだけなら、VS Code の拡張「Live Server」でも、次のどちらでも構いません。

```powershell
# このフォルダ（index.html がある場所）で実行
python -m http.server 8777
```

ブラウザで <http://localhost:8777/index.html> を開く。

> 初回は CDN からライブラリを、PLATEAU の CDN（`assets.cms.plateau.reearth.io`）から
> タイルを読み込みます。回線に応じて数秒で建物が順次描画されます。

## 自作モデルの追加（本題）

**通常は 01_building-builder（3Dモデリング）から自動で渡ってきます**（次章）。
手書きのモデルを足したい場合は、`js/main.js` の一番下に通常の Three.js コードで
メッシュを `scene.add()` できます。

- **座標系**: 原点 `(0,0,0)` = 設定した緯度経度の地表。**+Y=上 / +Z=北 / +X=西**、単位=**メートル**。
- PLATEAU 建物と同じ `scene`・`renderer`。`renderer` は `stencil:true` /
  `localClippingEnabled=true` 済みなので、ステンシルや `clippingPlanes` による断面表現に
  すぐ使えます。
- PLATEAU タイルは `window.__plateauTiles`（= `TilesRenderer`）と `tiles.group` で参照可能。

## 親アプリ（01_building-builder）との連携

ポータル（01）の **「🌐 地球モード」タイル**（単独起動）と、モデリング画面の
**🌍ボタン**（作った建物を持ち込む）から、このアプリが**全画面 iframe** として開きます。
02（マンセル）・03（夜間）と同じ方式で、**同一オリジンで配信されていること**が前提です。

**受け渡しは `sessionStorage`**（キーは `config.js` の `USER_MODEL_*_KEY`）:

| キー | 向き | 内容 |
|---|---|---|
| `earth_custom_glb` | 01 → 04 | 建物の GLB（blob URL）。無ければ街並みだけ表示する |
| `earth_model_heading` | 双方向 | 向き[rad]（北から時計回り） |
| `earth_model_offset` | 双方向 | 注目地点からの微調整 `{e, n}`[m] |
| `earth_focus_latlon` | 双方向 | 置いた地点 `{lat, lng}`[度]。01 の `lastPlacedLocation` と対応 |
| `earth_camera_state` | 双方向 | カメラ `{position, target, fov}`（mm・モデル原点基準）。行きも帰りも同じアングルで続く |

- **単位と軸**: 01 は **mm・+X=東・+Z=南**、こちらは **m・+X=西・+Z=北**。
  `USER_MODEL_SCALE`(1/1000) と `USER_MODEL_YAW_BASE`(180°) で合わせている
  （01 の軸の根拠は `viewManager.js` の4面図定義で `(-X,-Z)` の角を「北西から」としていること）。
- **置く場所は注目地点**。右下の地図で地点を選ぶとモデルもそこへ移り、地形の高さを拾って
  接地し直す。
- **切り抜きの大きさは親アプリの下部パネルからも操作できる**（01 の時刻スライダーの右隣の
  別パネル）。**0＝地球モードなし**で、50m以上に動かすと地球モードが起動する。
  - 親 → こちら: `window.setEarthClipSize(m)` ／ こちら → 親: `window.parent.syncEarthClipSize(m)`。
    HUD のスライダーとどちらを動かしても両方の目盛りが揃う（刻みは 10m で統一）。
  - ⚠️ **親へ「準備OK」を知らせるのは `main.js` の一番最後**。親はその折り返しで
    `setEarthClipSize` を呼んでくるので、`window.*` の入口を作り終える前に知らせると
    初期値が届かない（実際にこれで 300m のまま起動した）。
  - ⚠️ 01 の時刻パネルと 03 の時刻パネルは**同じ位置・同じ寸法で重なる**設計。
    01 側は右隣に切り抜きパネルを置くぶん 111px 左へずらしてあるので、
    03 も `body.embedded-modeling` で同じだけずらしている。**片方だけ動かさないこと。**
- **位置と向きはギズモのドラッグで操作する**（`TransformControls`）。HUD の
  「移動 / 回転 / 操作なし」で切り替え。数値入力や微調整ボタンは置かない。
  - 移動は**水平2軸だけ**（`showY=false`）。高さは常に地形から決まるので上下には動かさない。
  - 回転は**Y軸（方位）だけ**。刻みは `USER_MODEL_GIZMO_MOVE_SNAP`(0.5m) /
    `USER_MODEL_GIZMO_ROTATE_SNAP`(1°)。
  - ドラッグ中は `controls.enabled = false`（`dragging-changed`）でカメラ操作を止め、
    毎フレームの置き直し（`updateUserModel`）も飛ばす（位置はギズモが持っているため）。
  - ★**離した時点で【注目地点そのもの】をモデルの位置へ移す**（`commitGizmoDrag`）。
    こうしないとモデルだけが注目地点から離れ、建物タイルの読み込み範囲・切り抜き箱・
    地図の十字が付いてこない。移動が 1m 以下なら `setFocusLatLon` はタイルを
    読み直さないので、細かい詰めのドラッグで街並みが再読み込みされることはない。
  - three r169 以降 `TransformControls` は Object3D ではないので、
    `scene.add(gizmo.getHelper())` で足すこと。
- **⚠️ 接地は一度きりにできない**。地形は後から細かいタイルに置き換わるうえ、粗いタイルの
  三角形は盆地から山地までをまたぐので、初期の高さは数十m ずれる
  （実測: 市役所前で 標高43.4m のところが 103.6m）。
  → `core.js` の `dirty.userModel` が立つたびに置き直す（断面や眺望ポリゴンと同じ作法）。
  地形が十分細かくなるまで（`isTerrainReady()` が false のうち）は HUD に**「接地（仮）」**と出す。
- **切り替えの地続き感**（モデリング画面の絵から途切れずに繋ぐための作り）:
  1. **カメラを引き継ぐ**。親のカメラはモデル原点基準なので、こちらでモデルを置いた
     位置・向き（`userModelGroup` の position / rotation）を通して移し替える。画角(`fov`)も
     揃える。⚠️ 距離制限が親と違うので、向きは保ったまま距離だけ `minDistance`〜
     `maxDistance` に収めること（範囲外のまま渡すと `controls.update()` で一気に飛ぶ）。
  2. **街並みや地形を待たずにモデルを出す**（読み込み中の覆いを `hideLoading()` で先に外す）。
     PLATEAU 建物と地形はその周りに後から埋まっていく。
  3. **親は「出してよい」と言われるまで iframe を透明にしている**。こちらが
     モデル配置とカメラ合わせを終えてから `window.parent.showEarthSimulator()` を呼ぶ
     （夜間シミュレーターの `showNightSimulation` と同じ作法）。親側には保険のタイマーもある。
  4. **接地で高さが変わったぶんはカメラも一緒に動かす**（地形が細かくなるまでの間だけ）。
     画面の中でモデルが動かないので、変わっていくのは「周りの世界」だけになる。
  5. **帰りもアングルを引き継ぐ**。カメラ操作が一段落するたび（`controls` の `end`）に
     逆変換して `earth_camera_state` に預け、モデリング画面へ戻ると同じ向きで再開する。
- **読み込み中の表示は2種類ある**。全画面の `#loading`（起動直後だけ。モデルを出す時点で外す）と、
  左下の `#tileLoading`（「読み込み中…」＋スピナー）。後者は操作を妨げず、
  **地形が十分細かくなるまで／建物・地形の取得や解析が残っているあいだ**出したままにする
  （判定は `ui.js` の `updateHud`）。
- 復帰は、モデリングから来たときは右上の「✖ モデリング画面に戻る」（親の
  `window.closeEarthSimulator()` を呼ぶ）、ポータルから来たときは親の「ポータルに戻る」。
- **★ 閉じても破棄されない**。親は `src='about:blank'` にせず `visibility:hidden` で隠すだけに
  してあり、読み込んだ PLATEAU タイルと地形を抱えたまま待機する。2回目以降の切り替えは
  **街並みの再読み込みが起きず一瞬で戻る**（実測: 再入場後もタイル23枚・地形readyのまま）。
  - `window.pauseEarthSimulator()` … 描画ループを止める（rAF を積まないので完全停止。
    隠れている間にモデリング画面のCPUを食わない）。
  - `window.resumeEarthSimulator({from})` … ループを回し直し、
    `restartUserModelSession()` で**自作モデルだけ入れ替える**（モデリング側で建物を
    編集してから戻ってきても、ちゃんと新しいモデルになる）。
  - ⚠️ 隠すのに `display:none` は使わないこと。中の画面サイズが 0 になり、
    再開時にカメラの縦横比が壊れる。`visibility:hidden` なら大きさは保たれる。
- **iframe のときだけ HUD を下げる**（`body.embedded`）。親の「ポータルに戻る」ボタンが
  画面左上に固定表示されていて重なるため。

### 起動データの先読み（親アプリ側）

`01_building-builder/src/earthPrefetch.js` が、**このアプリが起動時に必ず取るもの**を
先にブラウザのキャッシュへ入れている。同じサイト内の iframe なのでキャッシュを共有できる。

- 温める対象: `index.html` と `js/*`、importmap に書かれた CDN ライブラリ、
  PLATEAU の tileset.json（LOD1×11・LOD2×9）、地形の layer.json、規制レイヤーのJSON 10種。
  **一覧は `js/config.js` を実行時に読んで作る**（config.js は import を持たないので
  importmap 無しで読める）＝ URL を二重管理しない。
- **b3dm（建物の中身）は温めない**。どれを読むかは実行時の走査で決まるので、
  当てずっぽうに取るとキャッシュを押し出して逆効果になる。
- 実測（開発サーバー）: 規制レイヤー10種 **2,906KB が転送量 0**（＝全部キャッシュから）。
  配信側のヘッダも良好（esm.sh は `immutable`、PLATEAU は `max-age=3600`）。
- 起点は「入口へのホバー」と「アイドル」。開かない人に8MB取らせないため、
  `navigator.connection` の `saveData` / 2G のときは何もしない。

## 場所・精細度・メモリの調整

`js/config.js`（全体の設定）と `js/section.js` 冒頭（切り抜き・断面まわりの色や閾値）の値で
調整します。

- `LOCAL_WIDTH_EW` / `LOCAL_WIDTH_NS`（既定 500m / 500m）… **注目地点まわり何mの建物を
  矩形で読むか**（全幅）。切り抜き箱の最大が 500m 四方なのでこれで過不足ない。
  リージョンは**交差判定**なので、地点が境界上にあっても跨る全タイルが読まれ取りこぼしは
  起きない。大きくすると範囲が広がるが重くなる。
  `LOCAL_HEIGHT`（既定 4000m）は鉛直方向の全高で、建物・地形の高低差を余裕を持って覆う値
  にしてあるので通常は触らなくてよい。
  ※ REPLACE 細分化の性質上「矩形に触れる親タイルはその子（葉）を全部読む」ので、矩形より
  少し広め（親1枚分）に読まれる。厳密な枚数にはならない。

- **2段階ロード**（`SEED_WIDTH` / `SEED_IDLE_MS` / `SEED_TIMEOUT_MS`）…
  起動時と地点移動時は、まず**指定地点を含むタイル1枚（＋その祖先）だけ**を読み、
  それが済んでから 500m 四方に広げる。
  - 第1段は矩形を `SEED_WIDTH`（既定 2m＝実質点）まで縮めて実現する。マスクは
    「タイルの境界体積と交差するか」の判定なので、点にすると**各階層で1枚ずつ**しか
    選ばれない。葉タイルは約 500×330m あるので、これ1枚でも指定地点まわりはかなり埋まる。
  - **⚠️ 鉛直（`LOCAL_HEIGHT`）は縮めてはいけない**。タイルの境界体積は実標高の位置にあるので、
    高さを潰すと標高のずれで交差せず1枚も選ばれなくなる。
  - 第1段→第2段の判定は**フレーム数ではなく時間**（`SEED_IDLE_MS`、既定 700ms）で行う。
    3D Tiles は外部 tileset JSON を読んで初めて子タイルが見えるので、「1枚読み終えた直後・
    次を積む前」に pending が一瞬 0 になる。数フレームでは通信の往復に足りず、まだ降りている
    途中で第2段に進んでしまう。恒久的な404などで止まる場合に備えて `SEED_TIMEOUT_MS`
    （既定 12s）で強制的に進む。
  - 実測（京都駅・同一走査深度）: 第1段=**12枚**、第2段(500m)=60枚。第1段は約 1/5。
  - 精細度（`errorTarget`）や優先度コールバックは触っていない。**触るのは「読む範囲」だけ**
    （優先度で解こうとすると REPLACE 細分化と噛み合わず逆効果になる。後述）。
- `TILESET_URLS_LOD2`（9区）/ `TILESET_URLS_LOD1`（全11区）… 区の tileset 配列。
  区URL一覧: `curl -s "https://api.plateauview.mlit.go.jp/datacatalog/3dtiles/26100-bldg-lod2-latest/tileset.json"`
  （LOD1 は `-lod2-`→`-lod1-`。他都市は `26100` を対象都市の 5 桁コードに）。
  建物は LOD2 の9区、山科(26110)・西京(26111)は LOD2 が無いので LOD1 で補完している。
- `t.loadAncestors`（既定 `true`）… **注目地点の中心からすぐ描画が始まる**ための設定。PLATEAU の
  階層は root=201KB / 中間=324KB〜1MB / 葉=5〜7MB と上位が桁違いに軽く、`true` だと粗い祖先を
  先に出して徐々に精細化する。`false` にすると重い葉が届くまで何も出ない（＝「待っても描画され
  ない」ように見える）。周縁に粗い白い箱が一瞬見えるのが気になる場合のみ `false` にする。
- `MAX_CAMERA_DISTANCE`（既定 4000[m]）… カメラを引ける上限。建物は局所しか無いが、眺望空間
  保全地域は全域（半径 8〜10km）を描くので広域を俯瞰したい要求がある。`controls.enablePan=true`
  にしてあり、右ドラッグ／Shift+左ドラッグで平行移動できる（`screenSpacePanning=false` なので
  地面に沿って動く）。地図ピッカーでの再センタリングも従来どおり使える。
- `sharedDownload.maxJobs`（既定 8）… 同時DL数。`FULL_BODY_FETCH_PLUGIN`（後述）により
  **本体転送まで含めた真の同時DL数**として効く。LOD2 の葉タイルは1枚5〜7MBあるので、
  多すぎると1枚あたりの完了が遅れて「いつまでも何も出ない」状態になる。少なめにして
  1枚ずつ確実に完成させる方が体感が良い。上げ過ぎると CDN への接続過多で HTTP/3(QUIC)
  が飽和し `ERR_QUIC_PROTOCOL_ERROR` が出るので注意。
- `sharedCache.minSize`（既定 64）/ `maxSize`（既定 800）… 保持タイル数。
  **⚠️ `minSize` は「最低これだけ保持する枚数」で、退避量は
  `max(min(itemList.length - minSize, unused), 0)` で決まる。つまり保持枚数が `minSize` を
  超えていないと不要タイルが1枚も退避されない**。局所描画の実使用は 90〜170枚程度なので、
  `minSize` はそれより小さくしておくこと（後述「仕組み」参照）。
- `ORIGIN_LAT` / `ORIGIN_LON` … 原点＝自作モデルの位置に据える緯度経度。
- `ORIGIN_HEIGHT` … 原点 `Y=0` に据える**楕円体高[m]**（＝その地点の地盤の楕円体高）。
  既定 64（京都駅の実測値）。別地点にするときは下の方法で求める。
- `camera.position` … 初期カメラ位置。
- `MAX_TEX_SIZE` … テクスチャの最大解像度（既定 512px）。※DL速度には効かない（メモリ/GPUのみ）。

### 中心の切り抜き（断面=灰＋黒ハッチ）

#### 断面の見せ方（`CAP_COLOR` / `CAP_HATCH`）

建築図面の断面表現に合わせて、**灰色の塗りつぶし＋黒の斜線ハッチ**にしてある。
切ると見える建物の【内側（裏面）】も同じ灰色（`makeInteriorCap`）。ハッチが付くのは
断面ポリゴンだけで、裏面はハッチ無し。

- **⚠️ 断面は不透明なので、ゾーンレイヤーのように alpha を落とすハッチは使えない**
  （何も起きない）。線の上だけ色をハッチ色へ `mix` する。
- **ハッチの向きは東西の面と南北の面で逆にしてある**（`i < 2 ? 45° : 135°`）。
  箱の角では必ず「X面とZ面」が隣り合うので、向きが変わると**隣接する2つの断面が
  別の面だと一目で分かる**（角で折れているのが読める）。
- **⚠️ `makeInteriorCap` にも `customProgramCacheKey` が要る**。無いと、同じ材質クラス・
  同じ設定の【断面ポリゴン用マテリアル】とプログラムが混線しうる
  （テクスチャの無い建物マテリアルはキーの材料が断面用とほぼ同じになるため）。
  ただし既定の `customProgramCacheKey` は `onBeforeCompile` の全文を返すので、
  素直に連結するとキーが巨大になる。**プラグインが自前で設定していた場合だけ引き継ぐ**
  （`hasOwnProperty` で判定）。

- `CLIP_SIZE_DEFAULT`（既定 300[m]）… 起動時の一辺。`CLIP_SIZE_MIN/MAX/STEP`（50/500/50）が
  HUD スライダーの範囲。
- `CAP_COLOR`（既定 `0xcc2222`）… 建物断面（塗りつぶし）の色。
- `GROUND_LINE_COLOR`（既定 `0x1a3cd8`）/ `GROUND_LINE_WIDTH`（既定 4px）… 地盤ライン（地表の
  輪郭）の色と太さ。「地形も切り抜く」ON のときだけ描かれる。
- `SOIL_COLOR`（既定 `0x9c6b3e`）… 地盤ラインの下、標高0m（海水準）までの「土」の色。
  側面4面と底面に描く。
- `SOIL_CONTOUR_COLOR`/`SOIL_CONTOUR_STEP`/`SOIL_CONTOUR_WIDTH`（既定 黒 / 10m / 1.5px）…
  土に引く等高線。**実際の標高（海水準基準）のキリのいい数字**に揃えて引く
  （後述の `ORIGIN_ELEVATION` を使って変換）。
- `SOIL_LABEL_WIDTH`/`SOIL_LABEL_HEIGHT`（既定 16m/8m）… 等高線に添える標高ラベル
  （"10m" 等）1枚のサイズ。側面4面すべてに、面の中心付近（そこに土が無ければ実際に
  ある区間の中点）に1枚ずつ配置する。キャンバスでテキストを描いてテクスチャ化している。
- `SOIL_MAX_RELIEF_FROM_MEDIAN`（既定 40m）… 外れ値を捨てる許容窓の**最小**幅。実際の窓は
  標高分布のばらつき（2〜98パーセンタイル幅）に応じて自動で広がるので、山地でも正当な
  地形は捨てられない（固定幅だと大文字山で地形が消えた）。
- `SOIL_MIN_SAMPLES_ACROSS`（既定 8）… **地盤ライン／土を描き始める条件**。
  起動直後は非常に粗い地形タイルしか無く、その三角形は**京都盆地から東山の山地までを1枚で
  またぐ**。無限平面で切ると切り口に山側の標高が混ざり、300m四方の箱の中なのに標高270mと
  いった値が出て**土が天高く伸びる**（毎回発生していた）。
  **これは外れ値除去では防げない**——サンプルが全部同じだけ粗いので「外れ値」にならないため。
  → 「地形の分解能そのもの」で判定する。**切り口の線分1本の水平長さの中央値**が
  `clipState.size / SOIL_MIN_SAMPLES_ACROSS`（300m四方なら 37.5m）を超えていたら、
  その地形は箱を解像できていないと判断して**何も描かない**（地形が細かくなると
  `markSectionDirty` が走って自動的に描かれる）。建物断面は地形と独立なので影響しない。
  実測（京都駅・300m四方）:

  | 状態 | 交線長の中央値 | 判定 | 描画 |
  |---|---|---|---|
  | 粗い地形（起動直後相当） | 866〜3076m | 解像不足 | 青線・土・等高線・底面・ラベル すべて非表示 |
  | 通常の地形 | 8〜16.8m | OK | すべて描画（土の最高 30.7m） |

  なお**土が青線より上に出ることは構造的に無い**（土のカーテンの上端は青線と同じ
  `prof[b]` を使っているため）。実測でも土の最高点＝青線の最高点で一致。
- `SOIL_MAX_SLOPE`（既定 1.0＝約45°）… 地盤プロファイルで「異常」とみなす勾配の上限。
  これを超える段差が**両隣に対して同方向**に現れたビンだけをスパイクとして平均で置換する
  （本物の連続斜面は残る）。4隅などに不自然な急勾配が出る場合は小さくする。
- `ORIGIN_ELEVATION`（既定 28.3、京都駅の実測値）… 原点の**標高**[m]（国土地理院の言う標高。
  `ORIGIN_HEIGHT` の**楕円体高とは別物**なので注意。日本付近はジオイド高が+36〜39m程度
  あるため、楕円体高64mでも標高は20m台になる）。土の底面・等高線の基準に使う。
  求め方: `curl "https://cyberjapandata2.gsi.go.jp/general/dem/scripts/getelevation.php?lon=経度&lat=緯度&outtype=JSON"`
- 実行時は `window.__dbg.clipState`（`{enabled, size, terrain}`）を直接書き換えても効く。

- **⚠️ 断面は「表示中」ではなく【読み込み済み】のメッシュから作る**。これが
  「断面が出ない／出るのが極端に遅い」のムラの正体だった。
  3D Tiles の REPLACE 細分化は**親を置き換えるのに兄弟タイル全部が揃う**必要があるため、
  読み込みが済んだタイルでも長時間ずっと非表示のままになる。断面を表示中メッシュから
  作っていると、その間ずっと断面が作れない。
  実測（市役所へ移動）: **修正前は48秒間ずっと「表示タイル1枚・断面3面」**のまま
  （その間に読込済は23枚まで増えていた）→ **修正後は4秒で4面そろう**。
  生成コストも 17〜20ms → 6〜11ms に下がった（下の最細LOD優先で粗い祖先を処理しなくなるため）。
  - **⚠️ 切り離されたタイルの `matrixWorld` は使えない**。子に置き換わった祖先タイルは scene から
    **切り離される**（`root.parent === null`。LRUには残るので `dispose-model` は発火しない）ので、
    `matrixWorld` が更新されず生の ECEF 座標（地球半径スケール）のまま残る。
    実際にこれで「土の高さが637万m」という不具合が起きた。
    → **シーンに繋がっているものと切り離されたもので処理を分ける**。
    繋がっているもの（表示中・非表示を問わない）は標準の `mesh.updateWorldMatrix(true, false)`。
    切り離されたものは `root.updateMatrixWorld(true)`（= グループ内ローカル）してから
    その `TilesRenderer` の `group.matrixWorld` を前から掛けてワールドへ。
    そのため `registerClipMeshes` で `__clipRoot`（scene ルート）と `__clipGroup` を覚えている。
  - **⚠️⚠️ やってはいけないこと: 一時的に `root.parent = null` にして `updateMatrixWorld` し、
    その後 `parent` を戻す**。戻るのは `parent` だけで `matrixWorld` はグループ内ローカルのまま
    残る。しかも Three.js の `updateMatrixWorld` は `matrixWorldNeedsUpdate` が立っていない限り
    子へ再計算を伝播しないので、**次のレンダリングでも直らない**。
    結果、**表示中タイルの行列が壊れて建物も地形も一切描画されず、断面・土・青線
    （ワールド座標で別に組むオブジェクト）だけが残る**という逆転現象になった（実際に発生）。
    シーンに繋がっているオブジェクトの `matrixWorld` は絶対に書き換えないこと。
    切り離されたものは描画に使われないので書き換えて構わない。
    回帰テスト: `buildSectionFill()` の前後で接続中メッシュの `matrixWorld` が
    **1つも変化しない**ことを確認する。
  - **「同じ枝で最も細かい LOD だけ」を使う（建物・地形とも）**。粗い祖先と細かい子が両方
    読み込み済みのことがあり、両方使うと壊れる。候補タイルの祖先を全部「置き換え済み」として
    除外すれば最細 LOD が自然に選ばれる。欠けたビンはプロファイル側の線形補間で埋まるので、
    絞っても青線は途切れない。
    - 建物 … 同じ建物の断面が二重にできる。
    - 地形 … **地盤ラインが実際より高くなる**。京都は盆地なので、粗い地形タイルは駅と
      東山の山地をまたぐ巨大な三角形を持つ。それを切断面で切ると山側の標高が混ざった
      高い交点が出る。「ビンごとの中央値なら細かい方に寄る」と考えて地形だけ絞らない実装に
      したことがあるが、粗い祖先が階層ぶん積み上がるとサンプル数で押し負けて中央値ごと
      持ち上がった（実測: 正解 25.8〜28.5m に対し 30m 等高線より上に描画された）。
  - **建物断面が地盤ラインより下にめり込むのは PLATEAU データ由来**（実装の不具合ではない）。
    実測（市役所付近・300m四方・506点）: 建物最下部と地形表面の差は**中央値 -0.1m**、
    **71%が±0.5m以内**で、ほとんどの建物は地形に正しく載っている。1m超めり込むのは**3.4%**。
    最大4.2mの箇所を調べると、国土地理院の1m DEM ではそこに**実際に約4.6mの段差**があり
    （30m西=38.6m / 東=43.2m）、PLATEAU は建物ごとに**単一の底面標高**（この建物は39.3m＝
    低い側）しか持たないため、高い側が必ず埋まる。
    しかも PLATEAU の**地形データはこの段差を再現していない**（60m区間で 43.5m の完全に平坦）。
    → **地形の `errorTarget` を上げても解消しない**（1まで下げても 43.7〜44.3m で平坦のまま。
    実測済み）。建物側と地形側で局所的な精度が違う、というデータ同士の食い違いなので、
    描画側では直せない。見た目を優先するなら断面を地盤ラインで切り落とす手はあるが、
    実データを隠すことになる。
  - **地盤ラインの検算方法**（高さがおかしいと思ったとき）:
    1. 国土地理院の標高APIで正解値を取る
       `curl "https://cyberjapandata2.gsi.go.jp/general/dem/scripts/getelevation.php?lon=経度&lat=緯度&outtype=JSON"`
    2. `groundLines[i].geometry` の頂点 Y から標高を出す（`標高 = y - SEA_LEVEL_Y`）
    3. **実際に描画されている地形メッシュを Raycaster で真下に撃って**標高を測る
    - 2と3が一致していれば断面計算は正しく、1との差は PLATEAU 地形データ自体の差
      （現 LOD の平滑化）。実測では 2と3が±0.5m で一致し、1に対しては一様に +1.5m 程度だった。
  - 同じタイル scene に複数メッシュがあると `updateMatrixWorld` が重複して O(n²) になるので、
    scene ルート単位で1回だけ更新する。
- `buildSectionFill()` は**先に `sectionFillGroup` を空にしてから**作り直すので、途中で例外が出ると
  「断面が消えたまま」になる。しかも `animate` 内で投げると以降の `renderer.render()` も飛ぶ。
  呼び出し側で try/catch し、失敗したら `sectionDirty` を立て直して次フレームで再試行する。

### 眺望空間保全地域（シェープファイルを地形に沿わせる）

京都市の眺望景観保全地域（五山送り火などの眺めを守る12区域）のポリゴンを、地形の起伏に
沿わせて重ねる。HUD の「眺望空間保全地域を地形に重ねる」で切り替え。

- **データ変換は事前にオフラインで行う**（ブラウザに shp パーサと投影変換を持ち込まないため）。
  ```bash
  python shp2json.py "眺望shapeデータ/眺望空間保全地域.shp" 眺望空間保全地域.json
  ```
  - 元データは **EPSG:2448（JGD2000 / 平面直角座標系 第VI系**・原点 lat36/lon136・k0=0.9999）。
    `.prj` に書いてある。JGD2000 は `TOWGS84[0,…,0]` なので WGS84 と同一とみなしてよい。
  - shapefile は `(x, y) = (easting, northing)` の順（日本の公式定義の X=北 とは逆）。
    北緯・東経に変換して京都になる方が正しい、で判別できる。
  - `pyproj` 等が無い環境向けに逆 Transverse Mercator（Snyder の級数）を自前実装している。
    順変換も入れてあり、起動時に往復誤差を表示する（実測 0.0000m）。
  - 出力は 100KB 程度。属性は `KUIKIMEISH`（区域名）と `KUIKIBANGO`（区域番号）を持ち出す。
    ⚠️ dbf の文字列は 50 バイト固定長で**多バイト文字が途中で切れる**ので
    `decode('utf-8','ignore')` して不正バイトを落とす。
- **「地形に沿わせる」実装**: ポリゴンを細かく分割し、各頂点の高さを地形から取る。
  - **高さは Raycaster で1点ずつ撃ってはいけない**。分割後は数千〜数万点になり重すぎる。
    → **一度だけ地形の高さグリッド（既定 20m セル）を作り、以後は双線形補間で O(1) で引く**。
    グリッドは表示中の地形メッシュの三角形を上から見て焼き込む（重心座標で高さを補間）。
    スカートは断面と同じく `geometry.groups[0]` で除外する。
  - **⚠️ 分割は「最長辺の二分割」で行うこと**。全辺を半分にする4分割は、三角形分割
    (ear clipping) が生む細長い三角形で破綻する。1m×3000m の三角形は 4分割だと 8段で
    65,536枚に爆発するが、最長辺だけ割れば数百枚で済む。
    実測（300m四方）: **4分割 26,770枚/117ms → 最長辺二分割 2,763枚/4ms**。
  - **⚠️ 分割前に描画範囲と交差しない三角形を捨てる**。眺望ポリゴンは1辺が数kmあるので、
    範囲外まで細かく割ってから捨てるのは完全な無駄。
  - **⚠️⚠️ 分割の打ち切りは「辺の長さ」ではなく【高さの誤差】で決める**。「高さの取得」と
    「三角形の分割」を同じ 20m にしていたら、起伏のある土地で**三角形の内部（頂点を結ぶ弦）が
    最大 22m も地形から浮いた**＝建物より高い位置にポリゴンが乗った（実測・岩倉付近）。
    頂点は grid 上にあるので誤差が小さく、**頂点だけ測っていると気づけない**
    （頂点 最大3.1m に対し重心 最大22.1m）。**必ず三角形の重心でも測ること。**
    → 最長辺の中点で「弦の高さ」と「地形の高さ」を比べ、`VIEW_AREA_HEIGHT_TOL` を超えたら
    更に割る。平坦地は粗いまま・急な場所だけ細かくなるので枚数を抑えたまま密着する。
    あわせて高さグリッドを 20m → `VIEW_AREA_GRID_CELL`(5m) に細かくした。

    | 分割条件 | 三角形数 | 生成 | 重心での浮き 最大 | 頂点での浮き 最大 |
    |---|---|---|---|---|
    | 辺20m一律（旧） | 123,200 | — | **22.1m** | 3.11m |
    | tol 0.6 / 最小辺 4 | 300,904 | 150ms | 2.11m | — |
    | **tol 0.4 / 最小辺 3** | 342,550 | 190ms | **1.74m** | 1.50m |

    ※ 上の枚数は「半径1500m・起伏のある土地」のケース。切り抜き ON なら範囲が箱まで縮むので
    桁違いに少ない。`VIEW_AREA_MAX_TRIS` に張り付くようなら `VIEW_AREA_HEIGHT_TOL` を緩める。
  - **残る「建物がポリゴンに覆われる」ぶんについて**: 浅い仰角の広域ビューでは、
    浮きをゼロ・`polygonOffset` 無効にしても見えている建物ピクセルの 12% 程度が
    半透明のポリゴンに覆われる（実測）。これは**地面に貼る半透明面の性質**と、
    **地盤より低い位置に底面を持つ PLATEAU 建物**（上記参照）によるもので、
    浮きを直しても消えない。
  - 高さが取れない（地形未ロード）三角形は描かない。HUD は「範囲内だが地形の読み込み待ち」と
    「そもそも付近に無い」を区別して表示する。
  - **⚠️ 高さグリッドは「表示中」ではなく【読み込み済み】の地形から作る**。表示中だけを使うと、
    視錐台の外に出たタイルが非表示になった瞬間に高さが取れなくなり、**カメラを回しただけで
    ポリゴンが消える**（実測: orbit で表示地域が 5→3 に減った）。断面と同じ誤り。
    修正後は9通りのカメラ姿勢すべてで三角形数・表示地域数が完全一致することを確認
    （地形の「表示中」枚数は 3〜19 と変動しているのに結果は不変）。
    ワールド行列の求め方は断面と共通化した（`computeClipMeshWorld` / `keepFinestLod`）。
  - **⚠️ 高さグリッドにも断面と同じ「絶対的な健全性チェック」が要る**（風致地区の実装中に発覚）。
    `keepFinestLod` は粗い祖先を落とすが、**細かい子が1枚も読めていない場所では
    誤差 78,492m の planet 規模のルートタイルが「最精細」として残る**。その三角形は
    局所ENU系で地球の裏側（Y ≈ -1.16e7）まで届くので、そのまま焼き込むとグリッドに
    1,000万m 級の値が入る（実測: 半径13kmのグリッド 196万節点のうち **2節点が -12,709,466**）。
    半径 8.5km の眺望ポリゴンでは当たらなかったが、13km に広げた瞬間に踏んだ。
    → 三角形の3頂点のどれかが `SECTION_SANE_Y_MIN/MAX`(-300〜3000m) の外なら**三角形ごと捨てる**。
    修正後は同じグリッドで標高 5〜916m（愛宕山924m・比叡山848mと整合）・異常節点 0。
    **半径を広げる変更は、それまで触れていなかった粗いタイルを踏みに行く**ことを忘れないこと。
- **Z ファイト対策は「浮かせ量」と「polygonOffset」で役割を分ける**。
  - 浮かせ量（`VIEW_AREA_LIFT`）はワールド単位なので、深度で見た余裕は**距離の2乗で痩せる
    ＝遠距離に弱い**。しかも近くでは実際に浮いて見え、大きくすると**建物がポリゴンの下に埋まる**。
  - `polygonOffset` の単位は**深度バッファの最小分解能(1LSB)**なので、**遠方ほど自動的に
    大きくなる＝遠距離に強く、しかもワールド上は浮かない**。ただし大きくし過ぎると
    地形だけでなく建物にも勝ってしまう（`factor -8 / units -16` にしたら実際に建物が埋まった）。
  - → **近〜中距離を浮かせ量、遠方を polygonOffset に担当させる**のが正解。
    実測（3姿勢／地形に勝つ最悪値・見えている建物が埋まる割合）:

    | 浮かせ量 | polygonOffset | 地形に勝つ | 建物が埋まる |
    |---|---|---|---|
    | 0 m | 無効 | 69.0% | 1.07%（＝下限） |
    | 0.2 m | -1, -3 | 99.4% | 2.79% |
    | **0.3 m** | **-1, -3** | **99.8%** | **3.09%** ← 採用 |
    | 0.4 m | -1, -3 | 99.9% | 3.41% |
    | 1.0 m | -1, -4 | 99.8% | 5.10% |

    「建物が埋まる」の下限 1.07% は、**地盤より低い位置にある PLATEAU 建物**ぶんなので
    ゼロにはできない（上の「建物断面が地盤にめり込む」参照）。
  - 計測方法: 地形に勝つ率＝建物を隠して `depthTest` on/off のポリゴン色ピクセル数の比。
    建物が埋まる率＝**「地形のみの絵」と「建物を足した絵」の差分**で*実際に見えている*建物
    ピクセルを特定し、そこがポリゴン色に覆われた割合。
    ⚠️ 建物だけを描いてマスクにすると**地形の裏に隠れた建物まで数えてしまい**、
    設定を変えても数字が動かない使えない指標になる（最初これで失敗した）。
- **切り抜き箱で一緒に切れる**。ポリゴンは地面に貼り付くものなので、建物用ではなく
  **地形と同じ `terrainClipPlanes`** に従わせている（＝「中心を切り抜く」＋「地形も切り抜く」が
  ON のときだけ切れる）。地形を全域表示しているのにポリゴンだけ宙で切れる不整合を避けられる。
  切り抜きが効いているときは作る範囲も箱に絞るので三角形数が大きく減る
  （実測: 半径1500m で 56,364枚 → 300m四方で 2,763枚）。
- **切り抜き OFF のときは【建物タイルの読み込み範囲と無関係に全ポリゴンを描く】**。
  以前は `VIEW_AREA_RADIUS`(1500m) で切っていたが、これは建物の読み込み範囲とも一致しない
  中途半端な制限だった。今は全 feature の頂点から必要半径を求めて描く（京都全域で 8〜10km）。
  - **効いていた制限は建物タイルではなく半径定数だった**。高さグリッド自体は広くしても安く、
    コストは「地形三角形を全部なめる」ぶんが支配的（半径10kmで 15〜39ms）。
  - **半径を広げたぶんはグリッドを粗くして相殺する**。`cell = max(VIEW_AREA_GRID_CELL,
    2R / VIEW_AREA_GRID_MAX_SIDE)` でグリッドの一辺を最大 `VIEW_AREA_GRID_MAX_SIDE`(1400) に
    抑える。あわせて `maxEdge = max(24, cell*2)` / `tol = max(0.4, cell*0.08)` も cell に連動
    させる（tol を据え置くと粗いグリッドを相手に無限に割り続けて三角形が爆発する）。
    粗くしても精度はさほど落ちない（実測の最大誤差: cell 5m=0.42m / 15m=1.28m / 30m=1.73m）。
  - 実測: **切り抜き OFF で 12地域全部・441,000〜460,000三角形・半径 8,495m・セル 12.1m・
    340〜723ms**。切り抜き ON 300m四方なら 1地域・3,493三角形・セル 5m・17ms（品質は従来どおり）。
  - 数百ms かかるので `main.js` の再構築は**実測時間に連動したスロットル**にした
    （`wait = max(500ms, 前回の所要 × 6)`）。重い日は自動的に間隔が空くのでカメラが固まらない。
- 調整用の定数: `VIEW_AREA_MAX_RADIUS`（既定 12000m。全域でもここで頭打ち）／
  `VIEW_AREA_GRID_MAX_SIDE`（既定 1400。高さグリッドの一辺の最大セル数）／
  `VIEW_AREA_GRID_CELL`（グリッドの最小粒度、既定 5m）／`VIEW_AREA_MAX_EDGE`(24m) /
  `VIEW_AREA_MIN_EDGE`(3m) / `VIEW_AREA_HEIGHT_TOL`(0.4m)（分割の下限・上限・許容ずれ）／
  `VIEW_AREA_LIFT`（地形から浮かせる量、既定 0.3m。Z ファイティング回避）／色と不透明度。

### カメラ操作（回転・平行移動・引き）

| 操作 | 動作 |
|---|---|
| 左ドラッグ | 回転（注視点まわりを周回） |
| **右ドラッグ / Shift・Ctrl + 左ドラッグ** | **平行移動（パン）** |
| ホイール | ズーム（注視点から 20〜`MAX_CAMERA_DISTANCE` m） |
| HUD の「注目地点へ戻す」 | 見る向きと距離を保ったまま注視点を注目地点へ戻す |

- パンは `controls.enablePan = true` だけで**右ドラッグと Shift/Ctrl + 左ドラッグの両方**が
  有効になる（OrbitControls の標準動作）。`screenSpacePanning = false` なので地面に沿って動く。
- **パンで動くのは注視点(`controls.target`)だけで、建物を読む注目地点(`focusLocal`)は動かない**。
  実測: 1,353m パンしても建物は読済24枚のまま・DL 0＝読み直しは起きない。
  注目地点自体を移すのは小窓の地図から。
- 迷子になりやすいので **「注目地点へ戻す」ボタン**（`recenterOnFocus`）を置いてある。
- **⚠️ カメラの引ける上限を変えたら霧も一緒に直すこと**。`MAX_CAMERA_DISTANCE` を
  2000→4000m にしたとき、霧が固定値(3000〜9000m)のままだったので**引いた先が真っ暗**になった。
  → `scene.fog` を `MAX_CAMERA_DISTANCE × 1.5 〜 ×4.5` に連動させてある。

### 眺望規制の「標高面」を斜面として表示する

眺望空間保全地域は、実務上は**建物の標高規制**のエリア。HUD の「眺望規制の標高面を表示」で、
その上限面（＝見通し線の天井）を半透明の斜面として描く。

**規制の意味**（例: 賀茂川右岸からの「大文字」＝区域39）:

| | 内容 |
|---|---|
| 視点場 | 賀茂川右岸の河川敷。点A（標高67.683m）〜点B（標高49.487m）を結ぶ**線**（`視点場.shp` に21点のポリラインで入っている。全長1,922m） |
| 視対象 | 「大」の字の**底辺** a–b（両端とも標高290.986m＝水平な線分。長さ約266m） |
| 標高面 | 「視点場上の**任意の点**＋1.5m」と a・b の3点で張る三角形の面。Pが動くので**平面の族**になる |
| 規制エリア | その三角形族を**水平投影**した和集合 |
| 規制内容 | 建築物の各部分がこの標高面を超えてはならない |

- **規制エリアは既に描いているポリゴンそのもの**。頂点構造で確認できる:
  `#0〜#11`＝視点場ライン（中間点→A、`#11`はAから4m）／`#12`≒a（18m）／`#13`≒b（12m）／
  `#14`≒B（17m）／`#15〜#23`＝視点場ライン（B→中間点）。
  つまり境界＝**［視点場ライン］＋［A→a の見通し線］＋［a–b］＋［b→B の見通し線］**で、
  視点場側（1.9km）が広く視対象側（266m）が狭い**扇形**になる。
- **複数の三角形が重なる点では最も低い面（min）が効く**。視点場のどこから見ても遮ってはいけないため。
- 勾配は A→a が水平4,477mで+223m（約1/20）、B→b が水平3,005mで+241m（約1/12）。
  川べり51〜69mから山側291mへ立ち上がる。

**面のデータは公式のものを使う**（条文の数値を12地域ぶん手入力する必要はない）:

```bash
python contour2surface.py 眺望shapeデータ 眺望規制面.json
```

- `規制値等高線.shp` に **`KISEITAKAS`（規制高さ）** 属性があり、806本・11地域ぶんの等高線として
  標高面が入っている。残る区域34（円通寺）は `円通寺標高規制.shp`（116点すべて「標高規制値110.2m」
  ＝**水平な天井面**）。合わせて12地域＝ポリゴンの数と一致する。
- 図面名（`CHOUBOUMEI`）→ 区域の対応は**点の内外判定で自動決定**している
  （区域45は5枚のポリゴンを持つので、区域番号ではなく個々のポリゴンに割り当てる）。
- **⚠️ 単一平面では足りない**。視点場が【点】の地域は完全な平面だが、【線】の地域は平面族の min
  なので非平面になる。等高線を単一平面で近似した残差（中央/最大）:

  | 地域 | 残差 |
  |---|---|
  | funehou / funedai / funemyou / kitamyou | **0.00 / 0.00m**（視点場が点） |
  | funayamahidari / takahou / katuratori | 0.06〜0.52 / 1.1〜2.4m |
  | funefune | 1.11 / 8.4m |
  | kamodai / kamofuna | 1.84・2.60 / 17.8・11.0m |
  | nishioujifuna | **5.49 / 26.5m** |

  → 等高線を**経緯度の規則格子**に焼き込み、隙間をラプラス補間で埋める方式にしている。
- **⚠️ 格子は EPSG:2448 のままにしない**。中央子午線が136度なので京都(135.76度)では
  子午線収差が約0.14度あり、4kmで約10mの回転ずれになる。経緯度の規則格子にすれば
  アプリの `lonLatToLocal` でそのまま変換でき、`config.js` の原点を変えても影響しない。
- **⚠️ セルサイズは地域ごとに自動で決める**。固定25mにしたら区域44（幅98mの細い帯）が
  5列しか取れず誤差が中央2.44m・最大10.25mに悪化した（他は0.1m台）。
  「短辺を20分割」に変えて中央0.49mまで改善。境界でも双線形補間が効くようマスクを1セル膨張させる。

**⚠️ 階段状に見える問題と、その2つの原因**（どちらも実際に発生させた）:

1. **等高線の値は2m刻みに量子化されている**。それを「確定値」として格子に焼き込むと、
   勾配1/20の場所では約40mごとに2mの段差ができ、面が階段状になる。**元データの問題ではない**。
   - ❌ **汎用のラプラス平滑化は失敗**。等高線を引力にして釣り合わせると段差は消えるが
     低周波の形まで動き、等高線との誤差が中央0.18→**0.55m**・p90 1.08→**4.10m**・
     1m以内89%→**61%** に悪化した。
   - ✅ **局所平面の当てはめ（移動最小二乗）が正解**。標高面は区分平面なので、窓の中の
     等高線セルに平面を当てれば量子化誤差が平均化されて消える。**滑らかさと精度を同時に改善**:
     段差 0.305→0.077m（kamodai）、誤差は中央 0.18→**0.13m**。折れ目は窓ぶん丸まるだけ。
2. **法線が「面ごと」になるとファセット（陰影の階段）が出る**。
   Lambert 陰影が三角形単位で変わるので、面が幾何的に滑らかでも階段状に見える。
   → **法線は格子の勾配から直接作る**（`limitNormal`）。三角形の切り方に関係なく必ず滑らかになる。
   索引付きにして `computeVertexNormals()` で平均する手もあるが、輪郭を三角形分割すると
   分割経路によって頂点座標が一致せず溶接が確実でないため、勾配から作る方が堅い。
3. **⚠️ 面を「格子セル単位」で作ると【縁が格子に量子化されてガタガタになる】**。
   横から見ると滑らかでも、**上から見ると縁が20mの階段**になる（実際にそう見えた）。
   → **規制範囲の輪郭（`ring`）を三角形分割し、高さだけを格子から引く**。
   縁は輪郭そのままの精度になり、三角形数も減る（区域39で 14,162 → **2,188面**）。
   分割は眺望ポリゴンの地形沿わせと同じ「最長辺の二分割＋高さ誤差で打ち切り」を流用
   （`subdivideTri` はサンプル関数を受け取る形に一般化した）。
   このため `眺望規制面.json` には輪郭も入れて**自己完結**させている。

**⚠️⚠️ 等高線が範囲全体に無い地域がある — 補間ではなく【平面の外挿】が必要**

`規制値等高線` は**規制範囲の一部にしか描かれていない**ことがある。実測:

| 図面 | 等高線があるセル | 無いセル | 等高線が覆う範囲 |
|---|---|---|---|
| kamodai（賀茂川右岸） | 6,892 | 0 | ほぼ全域 |
| **funedai（船岡山公園）** | **403** | **1,992（83%）** | 5,590m のうち **2,404m（43%）** |

これをラプラス補間＋データ範囲へのクランプで埋めると、**標高面が最大値184mに張り付いて
「大」の字（標高290.986m）に届かず山腹に突き刺さる**（実際にそう見えた）。

- ❌ **局所平面の勾配をセルごとに伝播させる**のも駄目。窓が小さく勾配に誤差があるため、
  2,400m（120セル）外挿する間に誤差が積み上がり「大」の底辺で **275.4m**（15.6m不足）。
- ❌ **MLS の値を等高線の範囲 `[hlo, hhi]` にクランプする**のも駄目。データ端では平面が
  範囲を超えて当然なので、クランプすると負の残差が生まれ外挿先まで運ばれる（**288.4m**）。
- ✅ **全域の等高線頂点に当てはめた平面を土台にし、局所のずれ（残差）だけを伝播**させる。
  平面そのものの地域（視点場が点）は残差≒0 なので平面の延長そのまま＝厳密。

**⚠️ 視点場が「点」の地域は、面が先端（視点場）まで届かない**

視点場が点の地域（船岡山公園など）の規制範囲は「**視点場を頂点・視対象の底辺を底とする三角形**」
なので、先端は必ず格子セル（20m）より細くなり、格子に値が入らない。
そのため面が視点場に収束せず途中で止まる。実測の欠け:

| 図面 | 全長 | 欠け（格子だけ） | 欠け（平面の予備あり） |
|---|---|---|---|
| funehou（法） | 4,277m | **240m** | **0m** |

**視点場でも複数の面が一致することが検証になった**:

| 標高面 | 視点場での標高 |
|---|---|
| 妙 / 法 / 大文字（視点場を共有） | **すべて 99.7m** |
| 船 | 112.9m |
| 左大文字 | 111.7m |

視対象も等高線も別データの3つの面が、共有する視点場でぴったり同じ値になる。
（船と左大文字は視点場の座標が少し違う＝公園内の別の場所が指定されている）

**両方の標高面が「大」の字で一致することが検証になった**（条例値 290.986m）:

| 標高面 | 「大」の底辺での値 | 差 |
|---|---|---|
| 賀茂川右岸から（kamodai） | **290.9m** | -0.1m |
| 船岡山公園から（funedai） | **290.4m** | -0.6m |

視点場も等高線も全く別のデータなのに、同じ視対象の上で 0.6m 以内に収束する。

**検算の結果**（3段構え）:

| 検証 | 結果 |
|---|---|
| 公式等高線 → 書き出した格子 | 中央 **0.13m** / p90 1.53m / 84%が1m以内（23,682点） |
| 格子 → 描画したメッシュ | **145.7m = 145.7m（完全一致）** |
| 条文から解析計算した値 | 148.4m（+2.7m。解析再現の誤差 p90 2.94m の範囲内） |

- **距離では絞らず【12地域すべて】を常に描く**。以前は `VIEW_LIMIT_RADIUS`(3km) 以内だけに
  していたので、京都駅では 12 地域中 11 しか出ず、残りは注目地点を近くまで移さないと現れなかった。
  実測: 全域でも **12地域 / 29,367面 / 21〜34ms**（3km制限時は 11地域 / 28,700面）＝
  12番目を足しても +667面で、絞る意味がない。
- **標高面は【格子JSONだけ】から作れる**——地形にも建物タイルにも依存しないので、
  JSON が届いた時点の1回で完成形になり、以後どこへ移動しても結果は同じ。
  そのため `setFocusLatLon` では作り直さない（`markViewLimitDirty` を呼ぶのはトグル操作と
  JSON 読み込み完了のときだけ）。検証: 京都駅／船岡山公園／円通寺／桂離宮の4地点で
  12地域・29,367面が完全一致、地点移動後も `geometry.id` が変わらない＝再生成ゼロ。
  ※ ページ読込直後から全域が揃うのはこの性質のおかげ。地形沿わせのポリゴン（`viewArea`）は
  地形の読み込み状況に依存するので、こちらは引き続き作り直しが要る。
- ポリゴンと同じく `terrainClipPlanes` に従うので、カットモデルでは天井面も一緒に切れる。
  **⚠️ 逆に言うと「中心を切り抜く」が ON のままだと標高面も 300m 四方に切られる**ので、
  全域を眺めたいときは切り抜きを OFF にすること（確認中に一度これで「出ていない」と勘違いした）。

#### HUD の構造（折りたたみ「景観・眺望規制」）

レイヤーが8つになって HUD が縦に長くなったので、**「景観・眺望規制」の折りたたみ**にまとめてある
（`.disclosure` / `.disclosure-body`。クリックで開閉）。

```
▸ 景観・眺望規制
    美観地区                （＋10区分）
    建造物修景地区           （＋4区分）
    風致地区                （＋第1〜5種・特別修景地域）
    自然風景保全地区          （＋第1・2種）
    古都保存法               （＋歴史的風土特別保存地区・歴史的風土保存区域）
    伝統的建造物群保存地区     （＋4地区）
    眺望空間保全区域          （＋眺望空間保全区域・標高面）
```

- **⚠️ メニューの並び順は描画順とは別**。`ZONE_LAYERS` の並びは
  **描画順・重ね順・浮かせ量の段差**を決めるものなので、見せたい順に並べ替えると
  重なりの前後関係まで変わってしまう（美観地区をメニュー先頭にしたいからと配列先頭へ移すと、
  市街地で美観地区が風致地区の下に潜って見えなくなる）。
  → メニュー順は `uiOrder` で持ち、`setupZoneUI` がブロックをその順に並べ替える。
- **眺望空間保全区域だけは `ZONE_LAYERS` ではない**（`viewAreaState` / `viewLimitState` を
  直に持つ別系統）。同じ「マスター＋行」の形を `setupZoneUI` の末尾で手で組み立てて、
  見た目だけ他のレイヤーと揃えている。
- **⚠️ 項目の間隔を等間隔にするには margin を消して flex の `gap` だけに任せる**。
  情報行（`.stats-line`）と凡例（`.legend`）は既定の `margin-top` を持っていて、
  しかも情報行は中身が空のことがあるので、そのままだと項目ごとに間隔がばらついた。
  `.disclosure-body .stats-line:empty { display: none }` で空の行を畳むのが要点。
- 表示名は「〜を地形に重ねる」を付けず、区域名だけにしてある。
  眺望空間保全**地域**は UI 上は**区域**と表記する（shp のファイル名は「地域」のままなので、
  コード内の URL・変数名・コメントは変えていない）。

#### HUD でレイヤーをまとめる（`group`）

`group` に同じ文字列を付けた**連続した**レイヤーは、HUD で1つのまとまりになる。
マスターのチェックが1つになり、凡例には **config の並び順どおり**に
「種別を持つレイヤーの種別行」と「種別を持たないレイヤーの行」が**混在して**並ぶ。

```
▼ 風致地区を地形に重ねる            ← group: '風致地区'
    第1種 / 第2種 / 第3種 / 第4種 / 第5種   ← fuchi の kinds
    特別修景地域                    ← fuchiShukei（別レイヤー。rowLabel で短く表示）
▼ 古都保存法の区域を地形に重ねる      ← group: '古都保存法の区域'
    歴史的風土特別保存地区
    歴史的風土保存区域
```

- **まとめるのは HUD の見せ方だけ**。描画・生成・`subtract` は今までどおりレイヤー単位で独立。
- 行のチェックは既定 ON で、実際に出るかは**マスターとの AND**。
  マスターが OFF のあいだ行のチェックは `disabled` にする。
- 凡例が1行だけになる場合（グループでない・種別も1つ）は、
  色見本をマスターのラベルに付けて凡例を出さない（同じものが2つ並ぶのを避ける）。

**⚠️ 種別を持たないレイヤーもある**。歴史的風土特別保存地区は 25 面すべて同じ区分なので
`zone2json.py` は `kind: null` を出す。config 側も `kinds: [{ kind: null, ... }]` の1件にして、
HUD では**種別チェックを出さずマスターのラベルに色見本を付ける**（マスターと同じものが
2つ並ぶのを避けるため）。情報行の「◯種別を表示中」も出さない。

- データは `zone2json.py` で事前に WGS84 の JSON にする（`shp2json.py` と同じ逆TM変換を使う）:
  ```bash
  python zone2json.py 眺望shapeデータ/風致地区.shp 風致地区.json 1.0
  ```
  ```bash
  python zone2json.py 眺望shapeデータ/自然風景保全地区.shp 自然風景保全地区.json 1.0
  ```
  **⚠️ 種別の表記はレイヤーごとに違う**（"風致地区第２種地域" / "第２種自然風景保全地区"）ので、
  位置ではなく `第(.)種` のパターンで拾っている。

  **⚠️⚠️ 種別の属性があるなら、名称の文字列から導くより必ずそちらを使う。**
  第4引数に属性名を渡すと、その値をそのまま `kind` にする:
  ```bash
  python zone2json.py 眺望shapeデータ/美観地区.shp 美観地区.json 1.0 LEGEND_COD
  ```
  美観地区は `LEGEND_COD`（凡例コード）を持っていて、**これが欲しい粒度そのもの**だった。
  MEISHOU は19種類に分かれているのに、凡例としては10区分にまとめたい——という食い違いが
  この属性1つで解決する（実データで確認済み）:

  | LEGEND_COD | 名称 | 面数 | MEISHOU の種類 |
  |---|---|---|---|
  | 110 / 120 / 130 / 140 | 山ろく型 / 山並み背景型 / 岸辺型 / 旧市街地型 | 6 / 6 / 10 / 40 | 各1 |
  | 210 | 歴史遺産型 一般地区 | 7 | 1 |
  | **220** | **歴史遺産型 歴史的景観保全修景地区** | **5** | **3**（祇園町南・上京小川・祇園縄手） |
  | **250** | **歴史遺産型 界わい景観整備地区** | **16** | **8**（西京樫原・先斗町・本願寺…） |
  | 401 / 410 / 421 | 沿道型美観地区 / 市街地型美観形成地区 / 沿道型美観形成地区 | 5 / 15 / 20 | 各1 |

  名称から `界わい景観整備地区` を含むかで判定することもできるが、命名の揺れに弱い。
  公式が付けている凡例コードがあるならそれが唯一正しい。

  **属性の値は数値でなくてもよい**（そのまま `kind` になる）。建造物修景地区は凡例コードを
  持たないが `MEISHOU` がちょうど4区分＝凡例そのものなので、`MEISHOU` を指定すればよい:
  ```bash
  python zone2json.py 眺望shapeデータ/建造物修景地区.shp 建造物修景地区.json 1.0 MEISHOU
  ```
  **新しい shp を足すときは、まず全属性の値を `collections.Counter` で数えて
  「値の種類数が欲しい凡例の数と一致する列」を探すこと。** たいてい用意されている。

  種別は「凡例の区分」でなくてもよい。伝統的建造物群保存地区は**4地区とも凡例が同じ**だが、
  `CHIKUMEI`（地区名）を種別にすれば**地区ごとに表示を切り替えられる**
  （`kinds` の色を全部同じにするだけ）。

#### 破線の外周線（`dash`）

`ZONE_LAYERS` に `dash: { dashSize, gapSize }`（ワールド単位[m]）を付けると外周線が破線になる。
京都市の凡例が破線の枠で表される区域（伝統的建造物群保存地区）に使う。

- **`LineSegmentsGeometry.computeLineDistances()` は線分をまたいで距離を積算する**ので、
  外周をセル幅で細かく刻んでいても破線が途切れずに続く（リングの切れ目で位相がずれるだけ）。
  もし積算されない実装なら、セルごとに破線が1つずつ入る不揃いな見た目になるところだった。
- 凡例の色見本も CSS の `border: 1px dashed` にして画面と揃える。

##### ⚠️⚠️ 外周線の浮かせ量を「面の浮かせ量 × 倍率」にしてはいけない

線が面に埋もれないように、外周線を `面の浮かせ量 × 1.5` の高さに置いていた。
**飛び出し格子（`grid.excess`）が入るまでは浮かせ量が定数 0.3m だったので隙間も 0.15m で
問題なかったが、場所ごとに数十mまで増えるようになった途端、その 0.5 倍がそのまま
線と面の隙間になり【線だけ宙に浮いて見える】ようになった**（破線にすると特に目立つ）。

実測（線の各点と、その真下の面の高さの差）:

| | 中央 | p90 | 最大 |
|---|---|---|---|
| 修正前（`liftAt × 1.5`） | 0.15〜0.36m | 最大 3.8m | **47.5m** |
| **修正後（`liftAt + 0.02m`）** | **0.02m** | **0.02m** | — |

線が面に埋もれないようにするのは **`polygonOffsetUnits`（深度バッファ側）の役目**なので、
幾何的な差は Z ファイトを避けるだけの最小値（`ZONE_LINE_LIFT` = 2cm）でよい。
**教訓: 「本体に比例させておけば安全」という書き方は、その本体が定数でなくなった瞬間に壊れる。**
  - **Douglas-Peucker で 1m 間引く**。元データは 10.4% の辺が 0.5m 未満と過剰に細かい。
    1m 間引きで 66,652 → 32,077頂点（48%）、JSON は 735KB に収まる。
  - **穴（内環）を分けて出す**。shapefile の規約で外環＝時計回り（符号付き面積が負）、
    内環＝反時計回り。271面中5面が穴を持つ（計9リング）。眺望空間保全地域には穴が
    無かったので、`ShapeUtils.triangulateShape(contour, holes)` を使うのは風致地区が初めて。
  - 種別は `MEISHOU`（"風致地区第２種地域"）から `第(.)種` で 1〜5 を取る。
- **⚠️ 三角形数を決めているのは「許容ずれ」ではなく【最大辺】だった**。山地なので
  「許容ずれを緩めれば軽くなる」と考えたが外れ。最大辺37mのまま許容ずれを 0.4m→5m と
  緩めても 229万→145万にしか減らないのに、最大辺を 37m→80m にすると 45万まで落ちる。
  面積で効く量なので、広いエリアではまず最大辺（＝グリッドの粗さ）を見ること。

  | セル | 最大辺 | 許容ずれ | 三角形 | 生成 | 浮き 中央/p90/最大 |
  |---|---|---|---|---|---|
  | 18.6m | 37m | 1.5m | 1,584,732 | 471ms | 0.00 / 0.57 / 7.9m |
  | **28.8m** | **58m** | **2.3m** | **982,019** | **529ms** | 0.00 / 1.10 / 7.0m ← 採用 |
  | 40.0m | 80m | 3.2m | 453,624 | 182ms | 0.12 / 1.67 / 10.0m |
  | 52.0m | 104m | 4.2m | 302,295 | 92ms | 0.23 / 2.27 / 17.8m |

- **描画コストは視線の角度で大きく変わる**。俯瞰では 982,019三角形で **118fps → 115fps**（+0.2ms）
  とほぼ無料だが、**浅い仰角で2レイヤー同時（2,192,145三角形・75.3MB）だと 116fps → 56fps**
  （+9.2ms）。三角形数ではなく**半透明の重ね塗り（フィルレート）**が効くため。
  56fps なら実用上問題ないが、両方を常時 ON で近景を見るなら重いことは意識しておくこと。
- 重いのは**生成**（1レイヤーあたり約0.8秒）の方なので、眺望ポリゴンと同じ
  「前回かかった時間に比例して間隔を空ける」スロットルを掛けている。
  **⚠️ 眺望ポリゴンとも、レイヤーどうしでも【同じフレームでは作らない】**（`heavyDone` と
  `zonesStep` が1フレーム1つだけ作る）。どれも 500ms 級なので、重なると1フレームが
  1秒を超えて明確にカクつく。
- **種別の切り替えは【作り直さず visible を付け替えるだけ】**。種別ごとに別メッシュを作って
  あるので、チェックを付け外ししても **0.4ms**（`geometry.id` が変わらないことで確認）。
- **⚠️ 暴走止め `ZONE_MAX_TRIS` は「通常運用で張り付かない値」にすること**。異常時の保険であって
  品質目標ではない。1,200,000 にしていたら自然風景保全地区（全域で約130万枚必要）が常に
  張り付き、上限に達した後の三角形が**粗いまま出て**いた（HUD の `上限に達した` で分かる）。

#### 重ね指定を読ませる（ハッチ＋重ね順）

3つのレイヤーは**山地で大きく重なる**。半透明の面塗りどうしを重ねると
混色になるだけで、「2つの指定が重なっている」のか「別の1色の区域」なのか区別できない。
→ **重なる側をハッチにする**と、下のレイヤーの色が隙間から見えて
**重なりがそのまま読める**。地図表現としての定石でもある。
`ZONE_LAYERS` の `hatch: { periodPx, widthPx, angle }` を付けるだけで切り替わる。

| レイヤー | 表現 | 読み方 |
|---|---|---|
| 風致地区 | 塗りつぶし | 緑一色 → 風致だけ |
| 風致地区特別修景地域 | 濃い赤の `angle: 45` の斜線 | 赤い斜線 → 特別修景地域 |
| 自然風景保全地区 | 青の `angle: 45` の斜線 | 青い斜線 → 自然風景 |
| 歴史的風土特別保存地区 | `angles: [0, 90]` のクロスハッチ | 格子 → 特別保存地区 |
| 歴史的風土保存区域 | `pattern: 'dots'` の点々 | 点々 → 保存区域（特別保存地区の外側） |
| （重なり） | 重ねて描く | 緑＋斜線、緑＋格子…がそのまま見える |

- **`angles` に配列を渡すとクロスハッチ**になる（各方向の縞の和集合）。
  GLSL では方向ごとの `smoothstep` の `min` を取る＝「どれか1方向でも線に乗っていれば描く」。
- **`pattern: 'dots'`** は正方格子に丸を並べる（`mod(gl_FragCoord.xy, period)` の中心からの距離）。

#### 重なりを「差し引く」（`subtract` ＝ ステンシル）

歴史的風土【特別保存地区】は【保存区域】の中にある更に厳しい区域なので、
**重なった所は特別保存地区の模様だけを見せたい**（格子と点々が重なると読めない）。
`ZONE_LAYERS` に `subtract: ['rekishi']` と書くだけで、面が差し引かれる。

**実装はポリゴンの論理差分ではなく【ステンシルバッファ】**:

1. 消す側（特別保存地区）のマテリアルに
   `stencilWrite / stencilFunc = Always / stencilRef = 1 / stencilZPass = Replace` を付ける。
   深度テストを通った画素にだけ印が付く＝**地形に隠れている所は印も付かない**ので整合する。
   ハッチの隙間（alpha 0）でもラスタライズはされるので、**面全体**が対象になる（狙いどおり）。
2. 消される側（保存区域）は `stencilFunc = NotEqual / stencilRef = 1` で
   「印が付いていない画素だけ描く」。

- **ポリゴンのブーリアン演算より圧倒的に良い**。堅牢なブーリアン実装は重いうえ、
  三角形の重心で内外判定するような近似だと**境界が三角形サイズ（24〜51m）でギザギザになる**。
  ステンシルなら**画素単位で厳密**、かつ幾何計算はゼロ。
- **消す側を非表示にすると自動的に元の全域が出る**（印が書かれなくなるだけ）。
- **⚠️ 消す側が【先に】描かれる必要がある**ので、`ZONE_LAYERS` では消す側を前に置く
  （`renderOrder` は配列順で決まる）。
- **⚠️ three.js は `stencilWrite = false` だとステンシルテスト自体が無効**になるので、
  「テストしたいだけ」の側でも `stencilWrite = true` にして `stencilZPass/Fail/ZFail` を
  すべて `Keep` にすること。
- **外周線は消さない**。「どこまでが保存区域か」は境界線で分かる必要があるため
  （＝重なった所は「特別保存地区の格子＋保存区域の外周線」になる）。
- ステンシルは毎フレーム `renderer.autoClearStencil`（既定 true）で消える。
  他で使っていないので値は 1 固定でよい（`ZONE_STENCIL_BIT`）。
- 実測（東山の俯瞰）: 特別保存地区を出すと保存区域の点々の **44%** が消えた。

- **画面ピクセル基準**（`gl_FragCoord`）にしてある。ズームしても縞の間隔が変わらないので
  遠景で潰れない。ワールド座標基準にすると地形に貼り付いた模様になるが、
  広域では縞が細かくなりすぎてモアレになるので採らない。
- 縞の位相は `gl_FragCoord.x*cos + gl_FragCoord.y*sin`。この式の勾配の大きさは常に 1 なので、
  アンチエイリアスの幅は `fwidth` を使わず **0.7px 固定**でよい
  （`mod()` の折り返しで `fwidth` が跳ねるのを避けられる）。
- 線の部分は面積が3割ほどしかないので、不透明度は塗りつぶし(0.34)より上げる（0.72）。
- **凡例の色見本も同じ斜線にする**（`repeating-linear-gradient`）。CSS の角度は時計回りなので
  `180 - angle` で合わせる。
- **重ね順は `ZONE_LAYERS` の並び順**。後ろのレイヤーほど手前に来るよう、
  幾何的な浮かせ（`ZONE_STACK_GAP` = 0.06m。近距離で効く）／`polygonOffsetUnits` の段違い
  （遠距離で効く）／`renderOrder` の3つを揃えて動かす。同じ高さに置くと Z ファイトで
  まだら模様になる。**⚠️ レイヤーを増やすと最後のレイヤーの浮きが積み上がる**ので
  （5レイヤーなら 0.3 + 0.06×4 = 0.54m）、増やしたら建物の埋まり具合を見直すこと。
- **ハッチにすると描画は逆に軽くなる**。実測（浅い仰角・2レイヤー同時）:
  塗りつぶし同士 **56fps** → ハッチ **77fps**。画素の約7割が完全に透明になり
  ブレンドが減るため。**5レイヤー同時（2,923,157三角形・100.4MB）で 70fps → 47fps**
  （ここまで来ると重なりも増えるので素直に落ちる。使うレイヤーだけ出すのが実用的）。

##### ⚠️⚠️ `onBeforeCompile` で踏んだ罠2つ（どちらも「面だけ描かれない」症状になる）

1. **`customProgramCacheKey` を必ず一緒に定義する**。three.js は `onBeforeCompile` の中身を
   プログラムのキャッシュキーに含めないので、同じ材質クラス・同じ設定のマテリアルが
   既にあると**改造前のプログラムが使い回される**。
2. **GLSL ES の予約語を変数名に使わない**。`float half = ...` と書いたら
   `ERROR: 'half' : Illegal use of reserved word` でコンパイルに失敗していた。
   しかも**コンソールには何も出ず**、面だけが描かれない状態になる。
   怪しいときは素の WebGL で試すのが速い:
   ```js
   const gl = document.createElement('canvas').getContext('webgl2');
   const s = gl.createShader(gl.FRAGMENT_SHADER);
   gl.shaderSource(s, 'precision mediump float; void main(){ float half=1.0; gl_FragColor=vec4(half); }');
   gl.compileShader(s);
   gl.getShaderInfoLog(s);   // → ERROR: 0:1: 'half' : Illegal use of reserved word
   ```
- **⚠️ 全域のときは範囲の中心を【注目地点ではなくデータの広がりの中心】に置く**。
  風致地区は京都駅から見て北に偏っているので、注目地点基準だと半径 16.8km 必要になり、
  同じ節点数だとグリッドが粗くなる（実測: 中心をずらすだけで 半径16.0km/セル35.6m →
  **半径13.0km/セル28.8m**）。しかも `FUCHI_MAX_RADIUS` で頭打ちになって北端が切れていた。
- 検証: 独立に作った 5m のグリッドを基準に、描画済みメッシュの三角形の重心で浮きを測ると
  東山 p90 0.06m / 北山 p90 0.26m / **西山（最も急）p90 2.02m・最大 10.61m**。
  切り抜き ON のときは範囲が箱まで縮んで **セル5m・許容ずれ0.4m** になるので、
  注目地点まわりは眺望ポリゴンとまったく同じ品質になる（実測: 嵐山300m四方で 5面2,841三角形／12ms）。
- 穴の検証: 9リングすべてで「穴の重心を含む三角形が 0 枚」を確認。
- 色は京都市の凡例に合わせて 第1種=緑 / 第2種=水色 / 第3種=黄色 / 第4種=紫 / 第5種=ピンク
  （`FUCHI_KINDS`）。HUD の色見本つきチェックはこの配列から組み立てるので、
  色や区分を変えても UI が勝手に追従する。

#### ⚠️ 急な山で「ポリゴンに穴が開く」問題と対策（`grid.excess`）

見る角度によって山の斜面でポリゴンが途切れる、という症状。**Z ファイトではない**。
ポリゴンは高さグリッドの節点を頂点にした平らな三角形なので、
**尾根のように節点と節点の間が盛り上がっている所では三角形が地形の下をくぐる**。
そこは地形が手前に描かれるので、穴が開いたように見える。

**⚠️ 「三角形を細かくする」でも「一律に浮かせる」でも解決しない**（実測。突き抜けた三角形の割合）:

| 対策 | 突き抜け | 備考 |
|---|---|---|
| そのまま（浮かせ0.3m・85万三角形） | 12.6% / 最大 12.7m | |
| 三角形を倍に（171万・生成812ms） | 7.6% | 倍のコストで半分にしかならない |
| 一律 2m 浮かせ | 5.8% | |
| 一律 5m 浮かせ | 1.7% | **平地でも 5m 浮いて建物が埋まる** |

→ **地形が飛び出している量そのものを測って、その場所だけ浮かせる**のが正解。

1. 高さグリッドを作った後、**各地形頂点について「実際の高さ − グリッド面の高さ」**を求め、
   最寄りの節点に max で置く（`buildExcessGrid`）。
   平面より上の最大値は必ず頂点にあるので、頂点だけ見れば十分。
2. それを**三角形の最大辺ぶん**、分離型の最大値フィルタで広げる。
   平らな三角形が尾根をまたぐ以上、**その三角形が覆う範囲の一番高い所まで持ち上げないと
   必ずどこかで刺さる**ので、この幅は調整値ではなく幾何から決まる。
3. 頂点ごとに `lift = FUCHI_LIFT + sampleExcess(x, z)`。

実測（西山ほか3窓＋市街地）:

| 広げ幅 | 突き抜け | 実際の浮き p90 |
|---|---|---|
| 0m（＝一律 0.3m） | 13.3% / 最大 9.95m | 0.30m |
| 29m（0.5辺） | 6.0% | 2.49m |
| **58m（1.0辺）** | **4.3% / p99 1.78m** | 5.56m ← 採用 |
| 86m（1.5辺） | 2.3% | 8.34m（浮きが増えるだけ） |

- **平地の浮きはどの設定でも 0.30m のまま**（中央値）。上がるのは起伏のある所だけなので、
  「建物が埋まる」問題は起きない（市街地の窓では浮き 0.30m ちょうど・突き抜け 0%）。
- 生成時間は 529ms → 633ms（飛び出し格子ぶん約100ms）。
- **切り抜き ON のときはセルが 5m になるので飛び出しもほぼ 0**＝近くで見るときは浮かない。
- 山での浮きが気になるなら `ZONE_GRID_MAX_SIDE` を上げて三角形を細かくすること
  （三角形が小さいほど覆う範囲が狭くなり、必要な浮かせ量も減る）。
- `buildTerrainHeightGrid` の第5引数 `excessRadiusCells` が 0（既定）なら飛び出し格子は
  作らないので、**眺望空間保全地域の挙動は一切変わらない**（実測でも三角形数・浮きとも不変）。

##### ⚠️⚠️ 評価は「三角形の割合」ではなく【画面のピクセル】で見ること

自然風景保全地区に**同じ方式をそのまま**適用したところ、三角形ベースの突き抜けは
奥山で 15%（風致地区は 4.3%）と出た。そこで測り方を変えようとしたが、いずれも失敗した:

| 飛び出しの測り方 | 突き抜け | 実際の浮き |
|---|---|---|
| **地形頂点 − グリッド面（採用）** | 風致 4.3% / 自然 15% | **平地 0.30m / 山 p90 5.6m** |
| 節点の接平面からのずれ | 0〜3.9% | 中央 30m / p90 65m（曲面では κL²/2 と過大） |
| 弦のたるみ（2階差分） | 0% | 中央 40m（広げる幅ぶん効きすぎ） |

**結局そのままでよかった**。画面上で「本来見えるべきポリゴン画素のうち、地形に隠された割合」を
測ると **風致地区 0.49% / 自然風景保全地区 0.20%** で、**同じ方式のまま自然風景保全地区の方が
むしろ良い**。三角形の 15% は「三角形のどこか1点でも潜っている」割合であって、
画面に出る穴の面積とは桁が違う。

**教訓: 見た目の問題は見た目の指標で評価すること。** 中間指標（三角形の割合）を最適化しに行くと、
突き抜けは消えても 40m 浮くような明らかな改悪に進んでしまう。計測は
「レイヤー非表示」「通常」「`depthTest` 無効」の3枚を描いてピクセルを比べるだけでよい
（`README` 下部の Z ファイト計測と同じく、**「あるべき姿」と「実際」の差分**で測る）。

### 建物を高さで色分けする（`HEIGHT_BANDS`）

HUD の「建物を高さで色分け（テクスチャ→色）」で、航空写真テクスチャと高さ区分の塗り分けを
切り替える。区分は京都市の高度地区の凡例に合わせて 10m / 15m / 20m / 31m（＋31m超）。
凡例は `HEIGHT_BANDS` から自動生成されるので、色や区分を変えれば表示も追従する。

- **PLATEAU の b3dm は建物ごとの属性を持っている**。`scene.batchTable`（属性表）と
  `_batchid`（頂点がどの建物に属するかを示す頂点属性、`Uint8Array`）の両方が入っている。
  実測で使える属性は60項目以上: `bldg:measuredHeight`（高さ）/ `bldg:usage`（用途）/
  `bldg:yearOfConstruction` / `bldg:storeysAboveGround` / `uro:...totalFloorArea`（延床面積）/
  `buildingStructureType`（構造）/ 淀川水系各河川の**浸水ランク・浸水深・浸水継続時間**など。
- **⚠️ `bldg:measuredHeight` は全タイルにあるわけではない**（実測で 3,219件／9,066件）。
  無い場合は `_batchid` ごとの**鉛直方向の広がり**から算出して代用する。
- **⚠️⚠️ 高さをジオメトリから出すときの落とし穴が2つある**（どちらも実測で踏んだ）:
  1. **ジオメトリ空間の Y は鉛直ではない**。b3dm の中身は ECEF 系なので geometry の +Y は
     「地球のY軸」であって「上」ではない。京都では鉛直方向のECEF-Y成分は約0.57しかなく、
     建物の**水平方向の広がりがYに大きく混入**する。実測: 属性18.9mの建物の geometry-Y 幅が
     **124.5m**、属性130.5m(京都タワー)で82.6m と全く対応しなかった。
     → **必ずワールド行列を掛けてから**Y範囲を測る（ワールドでは +Y=上）。
  2. **1つの建物のジオメトリはタイル内の複数メッシュに分かれることがある**
     （マテリアルごとの分割）。メッシュ単位で測ると屋根だけ・壁だけの断片になり、
     高さ0が多発する。→ **タイル（modelScene）全体で batchid ごとに集計**してから高さを決める。

  属性値との誤差の推移（実測・3,167件）:

  | 方法 | 中央誤差 | p90 |
  |---|---|---|
  | ジオメトリ空間のY（誤り） | 3.1m | 9.8m |
  | ワールドY・メッシュ単位 | 0.88m | 10.5m |
  | **ワールドY・タイル全体（採用）** | **0.04m** | 1.41m（81.4%が1m以内） |

- **実装は頂点カラー方式**（`color` 属性を書いて `material.vertexColors = true`）。
  ジオメトリを分割しないので**ドローコール数も三角形数も増えない＝描画コストは不変**。
  実測: 102メッシュ・89.6万頂点の着色で **初回49〜59ms / OFF 1ms / 再ON 10ms**
  （`color` 属性はジオメトリに保持して使い回す）。追加メモリは頂点あたり12バイト（10.25MB）。
  1タイルあたり約0.6msなので、タイルが届くたびに塗っても読み込みの妨げにならない。
- 切り抜き（カットモデル）と併用できる。外側が高さの色、切り口が灰色（`CAP_COLOR`）になる。
  ※ 以前は断面が赤（`0xcc2222`）で 31m超の色（`0xe0553c`）と紛らわしかったが、
  灰色＋黒ハッチにしたのでどの区分とも混同しなくなった。
- 色分け中はテクスチャを外す（排他）。OFF に戻すと元のテクスチャが復帰する。

### 場所を移した直後の読み込み

- **⚠️ ライブラリ標準では `downloadQueue.maxJobs` が本体転送を律速しない**。実装はこうなっている:
  ```js
  downloadQueue.add(tile, () => fetchData(...))   // ← fetch() のヘッダ受信で解決
    .then(res => res.arrayBuffer())               // ← 本体（5〜7MB）はキューの外
  ```
  つまり `maxJobs` が効くのはヘッダ受信までで、**本体転送はキュー外で無制限に並列実行**される。
  そのため地図で場所を移すと移動先の作業セット（数十枚）の本体が一斉に流れて共倒れになり、
  **「キューは空なのに `stats.downloading` が何十秒も減らない」＝建物がほとんど出てこない**
  状態になる（実測: `currJobs:0` なのに `downloading:50` が60秒間停滞）。
  → `FULL_BODY_FETCH_PLUGIN`（`priority: -100` で `fetchData` を最優先で担当）が
  `arrayBuffer()` まで読み切ってから解決し、読んだバイト列を `Response` に包み直して返す。
  これで1タイルのDLがキューの1ジョブに収まり `maxJobs` が本来の意味で効く
  （修正後: `currJobs:8` が常に飽和し、キュー残 70→10 と着実に消化、読込済 8→68 と継続増加）。

- **⚠️ 移動時は「前の場所のタイルを速やかに捨てる」処理が必須**。ライブラリの退避は
  rAF スケジュール＆1パス `unloadPercent` 分ずつなので、地図で場所を移して大量のタイルが
  一気に不要になる状況には追いつかない。`setFocusLatLon()` で `evictBurstFrames = 30` を立て、
  animate 内（**各区の `update()` の後**＝この時点で旧タイルが未使用になる）で
  `lruCache.unloadUnusedContent()` を1フレームに複数回まとめて呼んでいる。
  これは**進行中フェッチの中断**も兼ねる（`unloadUnusedContent` が `AbortController.abort()`
  を呼ぶ）ので、移動先のDL枠がすぐ空く。
- 実測（7回連続で市内を移動）: キャッシュは 64〜86枚で安定し `isFull()` は一度も true に
  ならず、移動ごとに建物が読み込まれ続ける。
- **⚠️ 読み込み優先度を「注目地点からの距離順」にしてはいけない**。3D Tiles の REPLACE 細分化は
  **親を置き換えるのに兄弟タイル全部が揃う**必要があるため、距離順にすると近い兄弟だけ先に
  来て遠い兄弟が最後まで残り、揃うまで表示に切り替われない（実測: 読込52枚なのに表示4枚が
  長時間続いた）。ライブラリ既定の誤差優先（粗い順）は階層ごとに揃うので粗→細と段階的に
  表示が進む。**注目地点を早く出したいなら「優先順位」ではなく「読み込む範囲を絞る」**のが正解。
- **場所によって必要タイル数は変わる**（実測: 同じ1km四方でも京都駅=60枚、市役所=74〜82枚）。
  市役所は繁華街で建物が密なうえ4区の境界付近にあり、区ごとに別tilesetなので祖先タイルの
  オーバーヘッドが4重にかかる（実測: 市役所では4区が同時に読みに行く）。移動先によって
  収束時間が違うのは避けられない。

- **⚠️ 「最初の地点は速いのに移動先は遅い」の最大要因はブラウザのHTTPキャッシュ**。
  PLATEAU の CDN は `Cache-Control: public, max-age=3600` を返す（実測）。つまり
  **一度読んだタイルは1時間ディスクキャッシュに残る**。開発中に同じページを何度も
  リロードしていると、初期地点（京都駅）のタイルはキャッシュから瞬時に返る一方、
  移動先（市役所）は 5〜7MB × 数十枚を毎回ネットワークから取る。
  この差は体感で桁違いになるが**コードの問題ではない**。
  → 公平に比べるには DevTools の Network で「Disable cache」を入れるか、
  タイルURLに `?cb=乱数` を付けてキャッシュを迂回する。
  （検証用ブラウザは `cache:'force-cache'` と `cache:'reload'` が同じ所要時間になり
  HTTPキャッシュが無効と判明した。そこでは京都駅も市役所も同じだけ遅い＝
  **コード側に「初期地点だけ特別扱い」は存在しない**ことの裏付けになる。）

- **地点移動時は TilesRenderer ごと作り直す**（`resetWardTiles()`）。
  LRU の退避バーストだけでは以下が引き継がれてしまう:
  - `downloadQueue` に積まれた**前の場所ぶんのジョブ**（移動先はその後ろに並ぶので、
    前の場所の 5〜7MB の葉を拾い終えるまで移動先が始まらない）
  - 各 TilesRenderer の走査状態（どのタイルを展開済みか）
  - LRU に残った tile と、それに紐づく `AbortController`

  `dispose()` → `makeWardTiles()` で作り直し、`wireSharedCacheAndQueues()` で
  キャッシュ／キューを新品に張り替えると、文字通り「ページを開き直した直後」と同じ条件から
  読み始められる。実測: 移動の瞬間に **DLキュー 60→0 / キャッシュ 60→0 / 全11区が新規**、
  共有配線と `maxJobs=8` `minSize=64` は再適用され、`scene` 内の group も 11 のまま
  （古い group はリークせず外れる）。
  - 実装メモ: `wardTiles` は**同じ配列オブジェクトを使い回す**（`length=0` してから push）。
    animate ループと `window.__dbg` が参照を握っているため。
  - `sharedCache` などは `let` にして張り替える。`runEvictBurst` はクロージャで参照するので
    自動的に新しいものを見る。
  - `clipMeshes` に残る建物メッシュは全部幽霊になるので、`__clipIsTerrain` でない要素を削除する
    （地形は別 TilesRenderer なので残す）。
  - 区の root JSON は再取得になるが 201KB×11 と軽く、ブラウザキャッシュにも載る。

- **⚠️ 検証時の落とし穴: 背面タブでは `requestAnimationFrame` が止まる**。
  `document.hidden === true` だと animate ループが回らないだけでなく、
  `PriorityQueue` のジョブ起動も rAF スケジュールなので**DLが1件も始まらない**
  （実測: 194秒間 `queued:66 / downloading:0 / loaded:0`）。
  自動化ブラウザで読み込み速度を測ろうとすると必ずこれに引っかかる。
  タイマー駆動に差し替えても背面タブは 1Hz に絞られるため、**読み込み時間の計測は
  前面タブでしか成立しない**。

### 地図ピッカー（右下の小窓）

- 国土地理院の標準地図を敷いた小窓。**クリックで拡大**、拡大地図で**ドラッグ=移動 / ホイール=拡縮 /
  クリック=その地点へ建物を移動**。赤い点＝原点（自作モデル位置）、青い十字＝現在の注目地点。
- `map.zoom` の初期値や `MAP_LAYER`（貼る地図の種類）は `setupLocationPicker()` 内で変更可。
- 地点選択は `window.__setFocusLatLon(latRad, lonRad)` を呼ぶだけでもできる（プログラムから移動）。

### 地形を「十分細かくなるまで出さない」（`TERRAIN_READY_ERROR`）

起動直後と地点移動直後は非常に粗い地形タイルしか無く、粗いタイルは1枚が数km〜数百kmを
またぐ平面なので、**注目地点の真上では実際の地盤より数百m も高い位置に出る**。それが
細かいタイルに置き換わるにつれて下がるため、**空から地面が降ってくる**ように見えていた。

PLATEAU 地形の `geometricError` は1階層ごとにほぼ半減する（実測）:

| 深さ | 1 | 4 | 8 | 11 | 13 | 15 | 17 |
|---|---|---|---|---|---|---|---|
| geometricError[m] | 78,492 | 9,633 | 602 | 75 | 18.8 | 4.7 | 0.15 |

`errorTarget = 6` の最終状態で表示されるタイルは 0.3〜9.6m だったので、
**「注目地点を覆う地形タイルの `geometricError` がしきい値以下」**を表示開始の条件にし、
それまでは地形グループ(`terrainWrap`)ごと隠す（読み込みは進める）。
地点移動時も同じ理由で隠し直す。

- **⚠️ しきい値は固定値にしてはいけない。カメラ距離に連動させること**。
  ```js
  const limit = Math.max(TERRAIN_READY_ERROR,           // 10m
    camera.position.distanceTo(controls.target) * TERRAIN_READY_ERROR_RATIO);  // 1%
  ```
  `MAX_CAMERA_DISTANCE` を 4000m に引き上げたとき、固定 10m のままだったので**引いた先で
  地形が永久に出なくなった**。3d-tiles-renderer は遠いほど粗いタイルで済ませるので、
  カメラ距離 3,970m では注目地点を覆う最精細の表示中タイルが 19.2m 誤差＝**しきい値を
  一生下回らない**。距離の 1% を下限にすれば、遠景では 39.7m まで許容されて開く。
- 起動直後の「空から降ってくる」対策は連動後もそのまま効く（近景ではしきい値が 10m のまま）。
  実測: カメラ距離 478m・粗い地形（覆うタイル 19.2 / 38.5 / 308.1 / 616.3m）→ `false` で非表示。
  カメラ距離 3,970m・同じ 19.2m のタイル → しきい値 39.7m で `true` になり表示。
- **⚠️ 「表示中か」を `scene` まで辿って判定してはいけない**。隠しているのは祖先の
  `terrainWrap` なので、辿ると常に非表示になり**永久に条件を満たさない**。
  タイル自身から `terrainTiles.group` までの `visible` だけを見ること。
- 実測: 粗い地形（表示中タイルの誤差 17.3〜4,127.7m）では `terrainReady = false` で非表示、
  精細化後（0.3〜9.6m）で表示に切り替わり、注目点の標高も正しい値になる。
- 検証時は `terrainTiles.errorTarget` を 4000 等に上げると起動直後の状態を再現できる。
  ただし `terrainReady` は一度立つと保持されるので、`setFocusLatLon` で少し動かして
  判定をリセットしてから観察すること。

### 地形（Terrain）まわり

- `SHOW_TERRAIN` … 地形の表示 ON/OFF（既定 true）。
- `TERRAIN_URL` … `https://tile.plateauview.mlit.go.jp/terrain/layer.json`（PLATEAU 地形配信。
  Quantized Mesh 形式・認証不要・CORS 開放・全国をカバー）。
- `terrainTiles.errorTarget` … 地形の粗さ（既定 6。背景なので建物ほど高精細でなくてよい）。
- `TERRAIN_VERTICAL_OFFSET` … 建物と地形の鉛直ずれ微調整[m]（通常 0。京都では両者が
  一致することを実測確認済み）。
- 地形の読込中プレースホルダ色は load-model 内の `color.setHex(...)` で変更可。

### 航空写真／地図（地形テクスチャ）

- `IMAGERY` … 貼れる地図の定義（国土地理院 XYZ タイル）。既定で 航空写真(seamlessphoto) /
  地理院地図(std) / 淡色地図(pale) / なし。`url` を足せば他の XYZ タイルも追加可能
  （Web メルカトル EPSG:3857 が前提。`levels` は最大ズーム）。
- `DEFAULT_IMAGERY` … 初期表示する地図（既定 `'photo'`）。
- HUD 左上のボタンで実行時に切り替え。切替は `ImageOverlayPlugin` の
  `deleteOverlay`/`addOverlay` で行い、地形タイルへ再合成される。
- **利用条件**: 地理院タイルは出典明記が条件（HUD にリンクを表示済み）。ズームの上限は
  タイル種別で異なる（航空写真・std・pale は概ね z18）。

**別地点での `ORIGIN_HEIGHT` の求め方**: いったん適当な値（例 0）で開き、ブラウザの
コンソールで地形読込後に次を実行すると、原点の地表の現在Yが出る。その値を
`ORIGIN_HEIGHT` に足せば地表が `Y=0` になる。

```js
// 原点(0,0)直上から真下へ地形表面Yを測る簡易版（読み込み後に実行）
const t = window.__plateauTerrain; let y = -Infinity;
t.group.traverse(o=>{ if(o.isMesh){ o.updateWorldMatrix(true,false);
  const p=o.geometry.attributes.position, m=o.matrixWorld.elements;
  for(let i=0;i<p.count;i+=200){const x=p.getX(i),Y=p.getY(i),z=p.getZ(i);
    const wx=m[0]*x+m[4]*Y+m[8]*z+m[12], wy=m[1]*x+m[5]*Y+m[9]*z+m[13], wz=m[2]*x+m[6]*Y+m[10]*z+m[14];
    if(Math.hypot(wx,wz)<120 && wy>y) y=wy; }}});
console.log('原点の地表 Y =', y, '→ ORIGIN_HEIGHT に (現在値 + この値) を設定');
```

## 仕組み・ハマりどころ（重要な非自明ポイント）

- **CORS 開放済み → プロキシ不要**。`assets.cms.plateau.reearth.io` は
  `Access-Control-Allow-Origin: *` を返すので、ブラウザから直接読める。
- **タイルは `.b3dm`**（glb ではない）。3d-tiles-renderer が自動処理する。glTF は Draco
  圧縮されているので `GLTFExtensionsPlugin({ dracoLoader })` を登録している。
- **座標は ECEF（地球中心・数百万m）**。`ReorientationPlugin({lat, lon, height})` で対象地点を
  原点・上方向 +Y に整列させる。自作モデルはこの原点基準で置ける。
- **地形は Quantized Mesh 形式**（3D Tiles ではない）。3d-tiles-renderer 同梱の
  `QuantizedMeshPlugin` で別の `TilesRenderer` に読ませる。`layer.json` を root URL として
  渡すだけ。**建物と地形は別々の `TilesRenderer` だが、同じ `lat/lon/height` の
  `ReorientationPlugin` で整列させると同一の世界座標に載る** → 建物が地形の標高の上に
  自動で乗る（実測: 京都駅原点で建物底面 ≈ 地形表面 ≈ Y0、ジオイド差なし）。
  地形の鉛直微調整用に親 `Group` で包んである（reorientation が子 transform を上書きしても
  効くように）。両方の `update()` を毎フレーム呼ぶ。
- **航空写真／地図は `ImageOverlayPlugin` + `XYZTilesOverlay`** で地形マテリアルに合成する。
  `XYZTilesOverlay` の既定投影は EPSG:3857（Web メルカトル）で、地理院 XYZ タイルと一致。
  地理院タイルは `Origin` 付きリクエストで `Access-Control-Allow-Origin: *` を返すので
  ブラウザから直接テクスチャに使える。オーバーレイはプラグインが各地形タイルの
  `MeshStandardMaterial` を `onBeforeCompile` で**ラップ**して合成するので、load-model 内で
  地形マテリアルを**置換してはいけない**（プロパティ変更のみ）。合成テクスチャの取得は
  プラグイン内部の `processQueue`（rAF スケジュール）で行われる。オーバーレイ画像の一時失敗
  （`load-error` で `e.overlay` が付く）は地形タイルの再読込ではなく
  `resetFailedOverlays()` で扱う。
- **描画が途中で止まる不具合の対策**（過去にハマった点。対策済み）:
  - LRU キャッシュの**バイト上限**（既定 0.4GB）は、テクスチャ付き LOD2 の見積りが過大で
    数タイルで「満杯」→ 新規DLがブロックされデッドロックする。→ バイト上限を `Infinity`
    にして**枚数**で管理する。
  - テクスチャが巨大でメモリを圧迫する。→ 読み込み時に `MAX_TEX_SIZE`(512px)へ縮小。
    これで狭い範囲なら実メモリ数十MB。
  - 一時的な取得失敗（`Failed to fetch`）は珍しくないので、赤いエラー表示は出さず数回だけ
    静かに再取得する（`load-error` で `lruCache.remove(tile)` → 次 update で再リクエスト）。
  - **`minSize` が実使用枚数より大きいと不要タイルが永久に退避されない**。退避量は
    `max(min(itemList.length - minSize, unused), 0)` なので、保持枚数が `minSize` を
    超えていないと `unloadUnusedContent()` を何回呼んでも1枚も減らない
    （実測: `minSize=200` で 172枚中 86枚が unused のまま 10回呼んで変化なし →
    `minSize=64` にすると同じ10回で 172→86枚に即減）。
    これを踏むと**地図で移動するたびに前の場所のタイルが残り続け**、
    `maxSize` に達した時点で `LRUCache.add()` が false を返して
    **新規タイルがリクエストすらされなくなる**（＝移動先の建物が出ない／激遅）。
- **【現行】注目地点まわり約9タイルだけを矩形(OBB)マスクで読む**。PLATEAU の LOD2 葉タイルは
  **1枚5〜7MB**と極端に重く（実測: 6.88MB / 7.20MB / 5.43MB）、広域では数百枚必要なので現実的
  な時間で終わらない（過去に2層構成＝LOD1広域+LOD2近傍で対処を試みたが、モデリング地点周りの
  高速性を優先する方針に転換し、広域自体をやめた）。`LoadRegionPlugin` + `OBBRegion`
  （`mask:true`）で、注目地点中心・東西`LOCAL_WIDTH_EW`×南北`LOCAL_WIDTH_NS`の矩形に交差する
  タイルだけを全区に対して読み込む。円形(Sphere)マスクではなく矩形(OBB)にしているのは、
  PLATEAU タイルの境界が不規則なため円形マスクだと選ばれる範囲がいびつな塊になるため
  （実際に円形で試して確認した）。
- **断面は GPU のトリックではなく CPU で幾何的に作る**（試行錯誤の末の結論）。
  - **なぜステンシルが使えないか**: three.js の `webgl_clipping_stencil` 方式（裏面 INCR /
    表面 DECR で数え、非0を塗る）は「表面の数と裏面の数が釣り合う＝**水密な閉じた立体**」が
    前提。PLATEAU の建築物モデルは**面がバラバラの集合**で全く水密ではない
    （実測: 463エッジ中 248 が境界エッジ／ループを辿っても 83 本中 14 本しか閉じない）。
    → シルエット全体が塗り潰される。**LOD1 も水密とは限らない**（実測: 3枚中1枚だけ）。
  - **「見えている面が裏面か」で塗る方式も不安定だった**。`depthFunc: Equal` は本描画
    （MeshStandardMaterial＋各種シェーダ改造）と印付けパス（MeshBasicMaterial）が
    **別プログラム**なので `gl_Position` が 1ULP ずれるだけで一致せず、
    「一瞬描画されて消える」症状になる。
  - **採用した方式**: 各三角形と切断面の**交線（線分）を CPU で集め**、端点が一致する線分を
    繋いで輪郭ループを作り（＝建物ごとに独立）、底面が無いために開いたループは両端を直結して
    閉じ、`THREE.ShapeUtils.triangulateShape` で三角形分割して面を張る。
    位相の破綻に強く、できあがるのは普通のメッシュなので**毎フレーム安定**する。
  - **地形の断面は「地盤ラインを青い太線」＋その下の「土」（側面4面＋底面、標高0mまで）**。
    地盤ラインは同じ交線計算を面を張らずに線分のまま描く（WebGL の `linewidth` は 1px 固定で
    効かないので `LineSegments2` + `LineMaterial`＝画面空間で太らせるアドオンを使う）。
    交線をそのまま使うと、地形メッシュの継ぎ目・欠け・LOD切替の隙間で線分が足りず
    **青線と土が途切れる**（大文字山のような急斜面で顕著）。そこで交線を
    **u方向に等間隔サンプリングした「連続プロファイル」に変換**している:
    ビンに入れ→各ビンの代表値は**サンプルの中央値**（粗いタイルと細かいタイルが同時に
    見えていてもサンプル数の多い細かい方に自然に寄る）→**欠けたビンは線形補間で埋める**
    ＝構造的に途切れない。土はこのプロファイルの隣接ビン間を標高0m(SEA_LEVEL_Y)まで
    下ろした四角形の帯、等高線はプロファイルを水平線で切った区間として描く。
  - **⚠️ 地形タイルのスカート除外は「傾斜の推測」ではなく「ジオメトリグループ」で行う**。
    `QuantizedMeshLoader` は `geometry.groups` で区切っており **group[0]=地表面**、その後に
    （solid なら底面キャップ、）スカート（タイル縁の垂れ下がり）が続く。以前は
    「ほぼ垂直な線分ならスカート」と傾斜で推測していたが、**急斜面では地盤線そのものが
    急勾配**なので正当な線まで捨ててしまい、青線と土が途切れる原因になっていた。
  - **⚠️ 切断面は「無限平面」なので箱の外（遠方）の地形との交線も入ってくる**。
    ビン番号を `clamp` して処理すると、遠方の全く無関係な標高が両端のビンに大量に積み上がり
    **4隅で異常に急な勾配**が出る（実機で発生）。`clamp` ではなく
    **箱の u 範囲で線分をクリップ（範囲外は完全に破棄、またぐ場合は境界で補間して切る）**のが正解。
  - **異常勾配の除去**: プロファイルに ①メディアン3フィルタ（孤立スパイクを除去、段差は保つ）
    → ②「**両隣に対して同方向に急**」なビンをスパイクと判定して両隣の平均に置換
    （本物の斜面は勾配の符号が揃って続くのでこの条件に当たらず残る。閾値は `SOIL_MAX_SLOPE`）
    → ③1-2-1 の軽い平滑化、の3段を適用している。
  - **⚠️ 標高0m（海水準）はシーンの `Y=0` ではない**。`Y=0` は原点の**楕円体高**
    （`ORIGIN_HEIGHT`）基準の地表であり、国土地理院の言う「標高」（ジオイド基準）とは
    ジオイド高（日本付近で+36〜39m程度）だけズレる。土を「標高0mまで」正しく描くには、
    原点の実際の標高（`ORIGIN_ELEVATION`、国土地理院の標高APIで取得）を使って
    `SEA_LEVEL_Y = -ORIGIN_ELEVATION` を求め、土・等高線の基準にする。これを取り違えて
    単純に `Y=0` までにすると、土がほぼ描かれない（実際にこの勘違いをして、ユーザーの
    「GSI地図では標高20m台のはず」という指摘で発覚した）。
- **⚠️ 断面計算に使うのは「表示中」のメッシュだけ**。レンダラーは非表示タイルをシーングラフ
  から外すため `matrixWorld` が未適用（＝ECEF の生値、大きさ数百万m）になり、混ぜると
  とんでもない位置の断面が生成される（同種の罠を過去に何度も踏んだ）。
  親を辿って可視性を確認し、`updateWorldMatrix` を呼んでから使う。
  **⚠️ さらに注意: `mesh.parent` が最初から `null`（＝粗い祖先タイルが子タイルに置き換わって
  描画ツリーから外れたが、LRUキャッシュにはまだ残っているので `dispose-model` は発火しない
  状態）だと、「親を辿るループ」は一度も回らずに `visible` フラグだけで通ってしまう。
  正しくは「`scene` まで辿り着けるか」を確認すること（`parent` チェーンを辿り `scene` に
  到達すれば表示中、`null` で途切れたら非表示とみなす）。実際にこれを取り違えて、
  古い matrixWorld（地球半径スケールの生ECEF値）を使ってしまい、土の高さが637万mになる
  不具合が起きた。**
- **⚠️ 上記を直しても、念のため「絶対的な健全性チェック」を入れておく**。個別メッシュの
  bbox でクランプするだけでは、その bbox 自体が壊れている場合に無力
  （↑の不具合はまさにこれだった）。原点からの相対Yが明らかに非現実的な範囲
  （既定 `SECTION_SANE_Y_MIN/MAX` = -300〜3000m）の交点は、個別メッシュの状態に一切頼らず
  無条件に破棄する。これにより、将来また別の経路で壊れたメッシュが紛れ込んでも、
  ありえない高さの断面が一瞬たりとも描画されることはない。
- **⚠️ それでも「範囲内には収まるが明らかにおかしい」高さは通り抜ける**（実機で実際に
  再発した）。最終防衛として**中央値ベースの外れ値除去**を追加している:
  地盤ライン・土・等高線が使う全ての交点の高さの**中央値**を求め、そこから
  `SOIL_MAX_RELIEF_FROM_MEDIAN`（既定40m）以上離れた交点を持つ線分は丸ごと破棄する。
  中央値は少数の異常値に影響されないので、地盤（青い線）より高い土は原理的に描かれなくなる。
- **標高ラベルの向き**: X面（u=z）と Z面（u=x）で「外から断面を見た人にとっての画面右方向」
  と u の増加方向が一致する面／しない面が実測で判明した（`faces` 配列の順で
  `[+X, -X, +Z, -Z]` のうち **+X面と-Z面は反転が必要**、-X面と+Z面はそのままで正しい）。
  `FACE_LABEL_FLIP_U` でこの2面だけ UV を左右反転している。他の断面要素（線・塗りつぶし色）
  は左右対称なので影響しないが、テキストラベルだけこの補正が必要だった。
- **クリップ面は常に4枚のまま保つ**。`material.clippingPlanes` の**枚数が変わるとシェーダが
  再コンパイル**されるので、切り抜きOFF時は枚数を減らすのではなく `constant` を遠方
  （1e9）へ飛ばして「何も切らない」状態にしている。建物用と地形用で配列を分けているのは、
  地形だけ切らない選択を再コンパイル無しで実現するため。
- **⚠️ OBB の作り方**: `OBB` は「箱形状(box、原点中心の固定サイズ)」と「箱を配置する行列
  (transform)」に分かれる。box は東西/鉛直/南北の半幅を持つ直方体として一度だけ作り、
  transform を毎フレーム `invGroupMat * translate(focusLocal)` で更新する
  （`invGroupMat` は `group.matrixWorld` の逆行列＝ワールド座標→ECEFへの変換。これにより
  box の東西/南北軸が group の回転＝再配置の向きに正しく追従して回転する）。更新後は
  必ず `obb.update()` を呼んで内部の頂点・平面キャッシュを再計算する。
- **⚠️ `SphereRegion`/`OBBRegion` はコンストラクタで渡した球/OBBを「コピー」して保持する**
  （参照しない）。そのため共有のオブジェクトを毎フレーム書き換えても効かず、**各リージョン
  自身の `region.sphere` / `region.obb` を更新する必要がある**。これを間違えると図形が原点に
  居座り、「タイルが一切読まれない」という原因の分かりにくい不具合になる。
  診断は中心座標の大きさが地球半径(約6371000)になっているかで確認できる。
- **全11区は区ごとに `TilesRenderer`**（同じ `lat/lon/height` の `ReorientationPlugin` で整列 →
  同一ワールドに境目なく連続）。3d-tiles-renderer は**視錐台外のタイルを読み込まない**ので、
  カメラが向いた区・タイルだけが順次DLされる（＝「向いていない所は最初から読み込まない」）。
  起動時に読むのは各区の root tileset.json（小さい JSON）だけ。**キャッシュとキューを全区で共有**
  （`wardTiles[i].lruCache/downloadQueue/parseQueue/processNodeQueue = 共有インスタンス`。3d-tiles-renderer
  は共有キュー用の `unifiedPriorityCallback` を持ち、レンダラーをまたいだ優先度比較に正式対応。
  ただし**最初の `update()` より前に差し替える**こと）。これにより (a) メモリ上限を全体で1つに管理、
  (b) 同時DL数を全体で `maxJobs`(10) に制限 → 1ホスト(PLATEAU CDN)への接続集中による
  HTTP/3(QUIC) 飽和＝`ERR_QUIC_PROTOCOL_ERROR` の多発を防止、(c)「最も近いタイルから」区をまたいで
  グローバルに優先ロード（＝見ている方向の区が先に出る）。区ごとに別キューだと 11区×maxJobs 本もの
  同時接続が集中して QUIC が飽和し、大量失敗→リトライで激遅になる。
- **描画ループはライブラリ標準の素直な形**（各区の `update()` を毎フレーム呼ぶだけ）。
  手動でキューを回すような小細工はしていない＝実ブラウザで自然に順次ストリーミングされる。
- import map で `three` を単一インスタンスに固定（esm.sh の `*` プレフィックスで依存外部化）。
  ES Modules のためローカル HTTP サーバー経由で開く必要がある。
